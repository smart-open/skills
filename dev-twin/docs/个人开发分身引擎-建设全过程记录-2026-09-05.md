# 🧬 个人开发分身引擎（dev-twin）建设全过程记录

*成文日期：2026-09-05 | 更新日期：2026-09-06 | 基于 dev-twin v1.1.3（暂定可用版本；v1.0 见 commit 916a872）| 画像库 v0.12*

> **一句话**：把"我"（软件开发工程师/架构师）的决策原则、编码习惯、架构偏好、工作方法提炼成结构化画像库，配一个按画像执行的引擎，让 AI 成为一个可自我进化的"加强版分身"——产出达到生产级，我只把控大方向。

---

## 一、这个项目解决什么问题

| 痛点 | 根因 | 解法 |
|------|------|------|
| AI 写的代码冗余、读不懂、难维护 | AI 按通用习惯工作，不按"我"的习惯 | 画像库 + 分身引擎，风格对齐 |
| dev-lifecycle 老技能费 token、工程大了跑偏 | 全量画像塞 prompt，无按需加载机制 | 分层画像 + 任务路由按需加载（≤3层） |
| AI 无法按我的思维方式做需求理解和架构决策 | 决策原则从未被显式结构化 | 决策原则画像层 + 决策分级（L1/L2/L3） |
| 经验无法沉淀，每次纠正都白白流失 | 无学习机制 | HITL 学习闭环：纠正→语料→复盘→入画像 |

**验收标准（铁律）**：可读可维护 / 性能·可扩展·鲁棒性 / 决策100%可追溯 / 自我学习迭代 / token可控——缺一不可。最终目标：达到80%完整画像，产出我简单review即生产级。

## 二、建设历程（九个阶段）

### 阶段1：战略奠基——五层深度对话

用 `strategic-advisor` 技能的五层对话（现状→本质→目标→路径→风险）把模糊想法变成清晰战略：

- **现状**：已有 dev-lifecycle 实践，暴露三类问题（冗余/费token/跑偏）
- **本质**：要的不是开发工具，是**数字分身系统**——画像引擎+决策引擎+学习引擎三层架构雏形在对话中浮现
- **目标**：3个月内达到80%画像；三大能力（思考决策/写代码/自我迭代）缺一不可但有先后
- **路径**：画像v0.1从简历+个人经验起步（最易结构化）；学习闭环=纠正→语料库→攒10项→复盘→确认入库
- **风险**：画像膨胀（→分层+按需加载+淘汰机制）、提炼失真（→双重校准）、需求理解最易失望（→决策留痕反推）

产出：`战略调研报告` + `行动计划`（四阶段10周路线图，9项行动含验证标准）。

> **方法论提炼**：先战略后建设。五层对话强迫把"我想要个分身"这种模糊诉求，逼成可验收、可分期、有风险预案的工程计划。

### 阶段2：画像提炼——从素材到结构化画像库

**素材**（按代表性排序）：个人开发经验 > 简历 > 工程代码（10W+行Java，git author 过滤本人提交）> 开发流程文档。

**提炼流程**：
1. AI 通读全部素材，逐条提炼候选画像条目
2. 每条标注三类：✅个人风格 / 🏆最佳实践 / ⚠️疑似历史包袱
3. 疑似项与用户逐条讨论定夺（包袱红线 vs 个人风格）
4. 用户决议直接写入 core 决议表（"理想中的我"覆盖历史惯性）

**双重校准**（防提炼失真的关键）：个人风格 × 业界最佳实践择优融合——技术实践向业界看齐，编码风格保留个人特色（如 Hutool 习惯、双网关模式、事务后置事件）。

**画像分层**（token可控的根基）：

| 层 | 内容 | 加载时机 |
|----|------|---------|
| core | 基础画像+8条决策原则+决议表 | 所有任务必读 |
| coding | Java编码习惯+包袱红线 | 编码任务 |
| architecture | 架构偏好+红线+深模块原则+原型思维 | 设计任务 |
| workflow | 九步流程+九大类审查+调试纪律 | 推进/审查任务 |
| tools | 技术栈+选型模式+AI方法论+安全基线 | 选型任务 |
| polyglot | 非Java语言业界最佳实践 | 多语言任务 |
| corpus | 原始语料库 | 仅复盘时 |

### 阶段3：引擎构建——dev-twin SKILL.md

引擎只做六件事（保持薄，知识全在画像）：

1. **画像定位**（5级优先级）：用户指定 > `PERSONA_DIR` > cwd > skill同级 > skill内置——外部覆盖内置，解耦不变
2. **任务路由**：按任务类型按需加载画像层，**同时激活≤3层**，禁止全量加载
3. **决策分级**：L1自主执行（画像明确覆盖，留痕）/ L2请示（画像未覆盖，AskUserQuestion列选项给推荐）/ L3强制确认（架构红线/安全/不可逆）
4. **执行九纪律**：决策留痕、token纪律、风格对齐、领域调用、测试智能适配、审查者视角自查、阶段交接摘要、事实自查决策请示、原子commit（*v1.1.1 三维度复审后增补第10条"任务边界纪律"（scope creep 防护），现为十条*）
5. **学习闭环**：纠正识别→写语料→攒10项→复盘确认→入画像（**绝不直接改画像层**）
6. **产出规范**：留痕格式统一（`coding#N / core#D编号 / 决议YYYY-MM-DD`）

### 阶段4：冒烟验证与学习闭环首跑

用两个真实场景跑端到端（银行流水CSV汇总工具等）：画像定位✅→路由✅→风格对齐✅→决策留痕（12项L1）✅→九步流程✅。

**首次纠正即闭环验证**：
- 纠正1：CSV不能全量加载，流式读取要从实现上解决而非靠提示规避 → 写入语料#1，代码同步修复
- 纠正2：error级别日志必须带异常堆栈 → 写入语料#2（用户选择留在语料等复盘，不立即入画像——**闭环纪律优先于效率**）
- 引擎自身也被纠正（Glob匹配目录不可靠→定位改用LS/shell）→ 补入SKILL.md

> **方法论提炼**：验证要"引擎+画像+闭环"三位一体测，只测产出代码不算验证通过。

### 阶段5：持续增强——按真实需求扩层

- **多语言**：用户提出需覆盖 Go/Python/Node/Rust/React/Vue/Taro/Kotlin/Tauri → 新建 polyglot 层。关键决策：**非Java按业界最佳实践执行**（不用等代码样本校准），通用红线（中文注释/日志脱敏/依赖最小化）全语言不变，被纠正时走学习闭环逐步进化为真实风格
- **技术栈清单**：Java 8/11/21多版本共存（写码前先确认版本）、LangChain/LangGraph双栈、RustFS 等事实类信息直接录入

### 阶段6：两轮外部蒸馏——榨干业界智慧

对外部优秀技能仓库（ECC、mattpocock/skills）做两轮蒸馏，原则：**只微调不动框架，每项先确认再落地**。

**第一轮**（README级）：审查者视角自查（fresh-context review）、阶段交接摘要（handoff）、拷问式需求对齐（grilling）、Agent.md含领域术语表（CONTEXT.md共享语言）。

**第二轮**（解剖7个skill+2份指南全文，榨剩余价值）：
- 调试六纪律（diagnosing-bugs）：**没有红灯命令禁止进入假设阶段**——先建能复现bug的单条命令
- 曳光弹任务拆分（to-tickets）：纵切全层、适配单个上下文窗口、expand-contract宽改造模式
- 双轴审查（code-review）：规格轴/标准轴分开报告互不遮蔽 + Fowler坏味道基线
- 深模块设计（codebase-design）：小接口藏大实现、删除测试、两个适配器才是真接缝
- 原型并行思维（prototype）：设计存疑造一次性原型，验证后只留决策
- Agent安全基线（ECC security）：致命三要素不共存、skill按供应链审查、HITL门=防记忆投毒
- 事实自查决策请示（grilling精髓）：问用户事实是浪费，替用户决策是越权

**明确不引入**（同样重要）：TDD红绿循环（与精简哲学互斥）、wayfinder重型机制、ECC平台技巧、285技能生态模式（正是dev-lifecycle的教训）。

**第四轮**（2026-09-06，仓库重组后 engineering/productivity 目录）：grilling 的前沿机制、domain-modeling 主体在前三轮已覆盖，本轮榨出 5 项增量入库——审查热点聚焦（git log 圈近期变更热区，不全库扫描）、ADR与改进审查交互纪律（承重理由否决→记ADR防重复建议；与ADR矛盾的候选仅值得重开才呈现）、选型一手源纪律（追溯官方文档/源码/spec，结论标来源）、merge冲突纪律（逐hunk追双方意图、不发明新行为、永不abort）、理解失败即澄清（消息含糊先重新表述确认）。architecture 层以"两点合并一条"写法入库（#50），落实软上限预警的"优先合并"原则。明确不引入：CONTEXT-MAP多域术语表（超微调边界）、teach/wizard/ask-matt/triage（场景不匹配）、跨人决策问卷（用户勾选放弃）。

**第五轮终榨**（2026-09-06，writing-for-agents/handoff/to-spec/implement）：**writing-for-agents 是全仓库价值密度最高的元知识**——agent 文档写作的完整方法论，核心入库 tools 层"Agent文档写作纪律"：两负荷模型（上下文负荷 vs 认知负荷，人是索引）、上下文指针措辞纪律（触发词前置/一支一触发/不重复正文身份）、环境即源真（只写查不到的约定/原因/坑，防缓存过期）、同址原则、禁令改正面表述（"不要X"把X拉进注意力反增触发概率）。连带吸收：handoff 的交接摘要引用不复制+脱敏（引擎纪律8微调一处）、to-spec 的规格阶段测试接缝决策（优先已有/最高可用/最少化，与调试六纪律"正确接缝"呼应）与实现决策不写文件路径（原型决策编码片段例外）、implement 的测试节奏（单测频繁/全量收尾）。淘汰机制同步升级为三问（no-op测试/引用频率/沉积检查）。不引入：SKILL-MECHANICS 引擎机制细节（引擎已薄）、CONTEXT-FORMAT 格式模板（术语表规则已有）、leading word 重构全库（分身已自然使用曳光弹/红灯/雾等领先词，按 no-op 测试无增量）。**过程教训入库**：本轮两次发生同文件并行编辑写覆盖（后写整文件覆盖先写），靠 P2 机械自查式全点终验兜住——同文件编辑必须串行，此教训已记入 dev-twin README 版本历史。**确认补全**：本轮 6 项入库未经事前勾选（自查 F1 发现），用户于同日追认全部 6 项，HITL 确认门闭环补全——此偏差本身记入流程警示：蒸馏类入库无论价值判断多清晰，勾选确认不可省。

### 阶段7：架构定型——自包含分发

`persona-zhutianwei` 从 skill 同级移入 `dev-twin/` 内：**别人拿走一个文件夹即得到带默认画像的完整分身技能**；换画像=替换内置目录，或外部任何位置放 `persona-自己/` 通过5级定位覆盖。

### 阶段8：思维分身实战——星枢物联网平台案例（2026-09-06）

以《星枢物联网平台（Nebula）产品设计说明书》为真实案例（中等偏上高并发分布式系统），跑完整"需求分析+架构设计"流程，产出《技术设计说明书》V0.1→V1.0（六版迭代）：

- **拷问式对齐**：4 项前沿决策确认（遥测设计点 1.7万条/秒、K8s+Compose 部署底线、行级租户隔离、5-8人/6个月工期）+ 口径类假设 AC 可观察化（首连成功率/无感切换）+ 雾项不预切（LLM选型/透传沙箱/多区域联邦）
- **架构设计**：决策摘要 D-01~D-13 结论前置；业务架构/C4 L1-L2/部署形态/三期演进蓝图；5 个关键流程时序图；容量估算链（峰值×5、70%水位红线）；E0-E15 曳光弹任务拆分（E1 第2周强制暴露技术风险）
- **用户驱动三轮演进**：
  1. 缺架构图/流程图/技术栈优势/LangChain 评估 → V0.3 补齐；ADR-006 选型 LangGraph（**human-in-the-loop 中断+checkpoint 是"高危操作必须用户确认"硬需求的原生实现**，LangChain4j 同构实现不成熟故弃）
  2. 接入内核语言拷问 → 评估采纳 Go：mochi-mqtt 扩展构建自研网关（ADR-001），第五章 Go 内核详设（goroutine-per-connection / 单连接内存≤1.5KB 预算 / 会话外置 Redis / 集群路由 / 三层背压）
  3. 语言跨度归并拷问（"Go+Java+Python 跨度大"）→ 三方案对比（维持三语言+降跨度纪律 / 一期全Go / 全Java），用户确认方案 A；评估留痕 ADR-001，新增 6.3 降跨度纪律（Go 窄内核 + 契约先行封顶集成成本）
- **决议兑现**：core 决议"新项目默认 PostgreSQL"→ D-10（JSONB+GIN 支撑物模型 50 键动态筛选）；"高并发接入组件可考虑 Go"→ ADR-001——上一轮试跑写入的决议直接复用命中
- **评审定稿**：2.2 两条口径假设评审确认（首连成功率 5min/按日；无感切换 3s+四项不丢）+ 机械自查（节引用/围栏闭合/上游文档映射）→ **V1.0 定稿**

### 阶段9：案例反向校准——首次完整学习闭环（2026-09-06）

用户主动发起复盘，以星枢案例实际行为反向校准画像：

- **正例确认**：13 条画像规则有效兑现（结论前置/ADR门槛与分级/拆分克制/一致性规避/容量估算链/曳光弹/雾判据/AC规范/决议复用），机制有效性得到实证
- **偏差定位 4 项，用户全选确认入库**：
  - P1 假设主动确认时机 → workflow（教训：口径假设存在 5 个版本才被确认——假设清单应交付即提请，不被动等待）
  - P2 文档任务机械自查 → workflow（教训：V0.4 插入第五章后修订说明声称"编号顺延"实际产生两个"七"——结构性变更后必须跑编号/引用/围栏/上游映射自查）
  - P3 ADR 备选空间广度 → architecture#49（教训：ADR-001 只评估了组件级选型，用户反向拷问"怎么归并"才补组合维度——备选评估须含组合/归并方向的显式排除）
  - P4 Go 窄内核纪律 → polyglot#9（用户首次确认的非 Java 决策先例，标注"星枢首例待二次验证"）
- **版本**：workflow v0.7 / architecture v0.6 / polyglot v0.5 / 画像库 v0.10；复盘 R1 归档 raw-corpus.md
- **里程碑意义**：三大能力（思考决策/写代码/自我迭代）全部经真实案例验证；"复盘→确认→入库→归档"闭环首次完整走通；dev-twin 定为 **v1.1 暂定可用版本**，阶段三/四转入实战完善期

## 三、关键设计决策（可追溯）

| 决策 | 备选方案 | 选择理由 |
|------|---------|---------|
| 画像分层+按需加载（≤3层） | 全量画像塞prompt | 根治费token+跑偏；dev-lifecycle教训 |
| HITL确认门（语料攒10项→复盘→确认入库） | 纠正自动写入画像 | 防画像污染/记忆投毒；用户始终掌控进化 |
| 决议表 > 决策原则 > 分层条目（优先级） | 无优先级 | "理想中的我"覆盖历史包袱；冲突有仲裁 |
| 引擎薄、知识全在画像 | 引擎内置规范 | 画像可替换=产品化根基；引擎改动最小化 |
| 非Java走业界最佳实践 | 等各语言代码样本校准 | 立即可用；学习闭环负责逐步个人化 |
| 决策留痕三种引用格式 | 自由描述 | 出问题可定位是画像错还是执行错 |
| 疑似历史包袱与用户逐条定夺 | AI自行判断 | 提炼失真是最高风险，人是最准的过滤器 |
| 内置默认+5级外部覆盖 | 纯外挂/纯内置 | 自包含分发 + 解耦可替换兼得 |

## 六、经验教训

1. **先战略后建设**——五层对话把模糊想法逼成可验收计划，避免直接开写导致返工
2. **引擎与知识分离是产品化根基**——画像可替换的设计从第一天就定下，阶段7水到渠成
3. **三层验证缺一不可**——产出代码、决策留痕、学习闭环要同时验证
4. **用户纠正是最珍贵的信号**——第一次纠正就是学习闭环的首跑素材；引擎自身也会被纠正（Glob目录匹配问题）
5. **不引入清单与引入清单同等重要**——两轮蒸馏明确拒绝TDD/wayfinder/平台技巧，防止画像膨胀走回老路
6. **闭环纪律优先于效率**——已确认的习惯仍留语料等复盘批量入库，保持流程一致性
7. **文档放docs/（gitignored），技能自包含入仓**——本地过程文档与可分发资产分离
8. **案例是最好的校准器**——画像规则的缺口（假设确认时机/文档机械自查/ADR组合维度）只有真实案例才能暴露；星枢案例一次暴露 4 项偏差并全部闭环入库
9. **结构性变更必须机械自查**——修订说明声称的与实际做的要一致验证（"编号已顺延"≠真的顺延），五查清单已入 workflow 层
10. **选型评估要覆盖组合维度**——组件级最优≠全局最优，备选空间须显式排除归并方向（architecture#49），防读者反向拷问才发现盲区
