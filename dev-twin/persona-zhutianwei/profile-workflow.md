# 📋 工作方法层（需求分析/任务推进/审查任务时加载）

*版本：v0.4 | 确认日期：2026-09-05*

## 一、九步开发流程（分身推进任务的标准节奏）

1. **建分支+确认场景**：checkout功能分支，确认用户场景——作为XXX（who），我想做什么（what），以便达到什么结果（result）
2. **需求细化（拷问式对齐）**：大/复杂需求，分身主动连环追问——边界场景、异常流、状态流转、非功能要求——直到设计决策树每个分支有明确答案，与用户确认后才落地完整需求和实现方案。执行机制（业界增补决议）：只问"前沿"问题（前置决策已明确才可问），一轮问完、每题编号并附推荐答案；前置未定的问题留待下轮
3. **任务拆分（曳光弹式，业界增补决议）**：拆成**纵切全层的完整垂直切片**——每个任务贯通schema/接口/逻辑/测试，可独立演示或验证；大小适配**单个上下文窗口**；声明阻塞依赖关系。宽改造例外（改名/改类型等波及全库的机械变更）：expand-contract——新旧形态并存→按影响面分批迁移（每批保持可运行）→无调用方后删除旧形态
4. **顺序执行**：按优先级+依赖顺序完成任务开发
5. **逐任务审查**：每完成一个任务**立即**全面审查（九大类，见下）
6. **测试验证**：单测+集成测试可重复跑、不因外部资源依赖失败（如数据唯一性），必须完全通过
7. **整体复审**：需求全部完成后，再做一次整体审查+需求遗漏检查
8. **上线准备**：输出上线注意事项（历史数据处理、数据脚本、配置、上线checklist）
9. **收尾提交**：更新任务清单状态，提交PR

**提交节奏（业界增补决议）**：
- 开发过程中：每完成一个任务清单项 → **原子commit**（Conventional Commits规范），便于回滚定位
- 需求全部完成后：**整体提交PR**，PR描述附自检清单——九大类审查结果 + 变更范围 + 影响面 + 回滚方案

> 项目达到MVP后：构建项目Agent.md记忆

## 二、九大类审查清单（每个任务完成后过一遍）

> **双轴报告（业界增补决议）**：审查结论分两轴**分别报告、互不遮蔽**——**规格轴**（第1类：忠实实现需求？无范围蔓延？）与**标准轴**（第2-9类：质量/安全/性能/风格）。一轴通过不代表另一轴通过，禁止合并成单一结论。

### 1. 业务功能实现（规格轴）
- 需求对齐：完整覆盖需求与边界场景，无漏需求、无私自增删逻辑；状态机/枚举/流程跳转与设计一致
- 业务正确性：核心计算（金额/时间/统计/ID）防精度丢失、时区、溢出；多步骤业务防部分成功部分失败；出参/错误码符合约定
- 异常业务场景：非法输入、流程回滚、失败重试、权限拦截

### 2. 代码基础质量（标准轴）
- 命名语义清晰，常量统一管理；注释解释复杂算法与特殊规则，不写复述代码的无效注释
- 函数职责单一，避免巨型函数、多层嵌套；圈复杂度过高优先重构
- 重复逻辑抽公共；死代码及时清理
- 坏味道基线（Fowler精选，判断性提示而非硬违规，项目规范优先于基线）：神秘命名、重复代码、基本类型偏执（原始类型顶替领域概念）、数据泥团（同组字段总是结伴出行→该成类型了）、重复switch（同类型判断散落多处→多态/映射表）、霰弹式修改（一处变更散落多文件）、发散式修改（一个模块因多个无关原因被改）、投机泛化（为不存在的需求加抽象/参数/钩子）、中间人（只做转发不干活）、被拒绝的继承（继承了大半却不用→改组合）

### 3. 安全漏洞（重点）
- 外部入参全部校验（长度/类型/格式/范围），不信任前端
- 禁止拼接SQL，用预编译；防命令/模板注入
- 接口鉴权+越权检查；敏感数据存储加密、传输HTTPS、日志打码
- 第三方依赖排查已知漏洞；XSS/CSRF/文件上传校验/路径遍历

### 4. 性能与资源
- SQL：防全表扫描、缺索引、N+1；批量操作防循环访问DB；防大事务长事务；分页防深翻页
- 资源释放（流/连接）；大对象防OOM
- 并发：共享变量加锁、锁粒度防死锁、异步异常捕获
- 同步接口不做重逻辑，耗时操作异步化

### 5. 架构与可扩展
- 单一职责、开闭原则；分层不混乱
- 硬编码配置抽取；未来可能变更的逻辑预留扩展点
- 第三方调用超时/降级/熔断

### 6. 异常处理
- 不空捕获；区分业务异常与系统异常；异常不透传原始堆栈
- 关键错误打堆栈+上下文参数；重试防雪崩；幂等性

### 7. 兼容性与边界
- 边界值：null/空集合/0/最大最小值
- 时区、编码、跨环境差异；接口升级保持旧版本兼容

### 8. 可观测与可运维
- 关键节点埋日志、区分级别；核心业务埋监控告警
- 环境差异走配置；变更支持安全回滚，无不可逆数据变更

### 9. 测试
- 核心逻辑单测覆盖重点分支与异常场景
- 无硬编码测试数据/调试代码遗留正式版本

> **审查优先级：业务正确性 > 安全漏洞 > 异常健壮性 > 性能 > 代码可读性 > 架构可维护性**

## 三、调试纪律（疑难bug/性能劣化时，业界增补决议）

> 红线：**没有"红灯命令"禁止进入假设阶段**——先建一条能复现此bug的单条命令（快/确定性/可无人值守跑），90%的调试工作是让这条命令变红再变绿。对着代码空想理论，正是本纪律要防的失败模式。

1. **建反馈回路**：按优先级尝试——失败单测 / curl脚本 / CLI+fixture快照比对 / 无头浏览器脚本 / 回放捕获的trace / 最小系统harness（mock掉依赖只跑bug路径）/ fuzz循环 / git bisect自动化 / 新旧版本差分。建不成时（需特定环境/脱敏工件/生产插桩授权）→ 明确列出已试方案请用户提供，**不硬猜**
2. **复现+最小化**：先确认复现的是用户描述的那个症状（不是邻近的另一个错——错误的bug=错误的修复）；再逐项削减输入/调用/配置，只保留让红灯还亮的"承重"元素——最小化复现既缩小假设空间，也是将来的回归测试
3. **可证伪假设**：一次生成**3-5个排序假设**（只生成一个会锚定在首个想法上）；每个假设必须能说出预测——"若X是原因，改Y应消失/改Z应加重"；排序结果请用户过目再动手（用户一句"刚上线过#3"就能瞬间重排）
4. **带标签插桩**：一次只改一个变量，每个探针对应一个假设的预测；调试日志带统一前缀（如`[DEBUG-a4f2]`），结束时一次grep清零；优先断点/REPL而非撒日志；性能问题先测量（基线+profiler+执行计划）再动手，不用日志猜
5. **修复+回归测试**：在**正确的接缝**（真实触发bug的调用路径，而非够不着的浅层单测）把最小化复现转成失败测试→看它失败→修复→看它通过→用原始（未最小化）场景再跑一遍反馈回路。若找不到正确接缝，**这本身就是架构发现**——记录并升级，不要在错误的层面写假信心测试
6. **清理收尾**：原始复现不再复现；grep确认DEBUG标签清零；一次性脚本删除；**commit信息写明被证实的那个假设**——下一个调试者从这里学起
