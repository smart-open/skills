# 📋 工作方法层（需求分析/任务推进/审查任务时加载）

*版本：v1.1 | 确认日期：2026-09-11*

## 一、九步开发流程（分身推进任务的标准节奏）

1. **建分支+确认场景**：checkout功能分支，确认用户场景——作为XXX（who），我想做什么（what），以便达到什么结果（result）
2. **需求细化（拷问式对齐）**：大/复杂需求，分身主动连环追问——边界场景、异常流、状态流转、非功能要求——直到设计决策树每个分支有明确答案，与用户确认后才落地完整需求和实现方案。执行机制（业界增补决议）：只问"前沿"问题（前置决策已明确才可问），一轮问完、每题编号并附推荐答案；前置未定的问题留待下轮。**拷问维度与需求产出物模板见二**
3. **任务拆分（曳光弹式，业界增补决议）**：拆成**纵切全层的完整垂直切片**——每个任务贯通schema/接口/逻辑/测试，可独立演示或验证；大小适配**单个上下文窗口**；声明阻塞依赖关系。宽改造例外（改名/改类型等波及全库的机械变更）：expand-contract——新旧形态并存→按影响面分批迁移（每批保持可运行）→无调用方后删除旧形态
4. **顺序执行**：按优先级+依赖顺序完成任务开发
5. **逐任务黑盒审查**：一个任务**完整做完之后**再审查（不边做边审）；审查必须**黑盒**——派无会话上下文的子代理按规则独立审查（机制见三"黑盒审查机制"），审查问题闭环修复后进入下一任务
6. **测试验证**：单测+集成测试可重复跑、不因外部资源依赖失败（如数据唯一性），必须完全通过；**测试节奏**——单测试文件/相关测试频繁跑快速反馈，全量套件收尾跑一次（业界增补决议）
7. **整体黑盒复审**：需求全部完成后，再派一次黑盒子代理做**整体审查+需求遗漏检查**（输入同白名单三项：审查规则 + 原始需求与AC + 全部产出物，同样不带过程上下文）
8. **上线准备**：输出上线注意事项（历史数据处理、数据脚本、配置、上线checklist）
9. **收尾提交**：更新任务清单状态，提交PR

**提交节奏（业界增补决议）**：
- 开发过程中：每完成一个任务清单项 → 黑盒审查通过 → **原子commit**（Conventional Commits规范），便于回滚定位
- 需求全部完成后：**整体提交PR**，PR描述附审查结果清单（**以黑盒审查报告为准**）——变更范围 + 影响面 + 回滚方案

**交互与合并纪律（业界增补决议）**：
- **理解失败即澄清**：用户消息含糊或上下文缺失时，先用已有上下文重新表述确认理解（"你的意思是X还是Y？"），不自意揣测执行
- **merge冲突**：逐hunk追双方原始意图（commit/PR/issue）；保留双方意图，不兼容时按合并目标取舍并记录权衡，**不发明新行为**，永不`--abort`；解决后跑typecheck/tests修复被破坏项

> 项目达到MVP后：构建项目Agent.md记忆

## 二、需求分析方法论（九步流程第2步的展开）

### 拷问维度清单（配合"只问前沿、一轮问完、编号+推荐答案"机制）

| 维度 | 必问问题 |
|---|---|
| 角色与场景 | who/what/result；触发频率（实时交互/低频批量）；涉及角色矩阵，各自视角差异 |
| 规则与状态 | 状态机全图（状态×事件→迁移）；规则例外与灰度地带；流程能否回退、如何回退 |
| 边界与异常 | 同单并发修改怎么办；多步骤部分失败怎么办；上游数据错误/迟到怎么处理 |
| 数据要求 | 量级（当前值+增长率）；保留周期与归档策略；敏感级别（对应日志脱敏决议） |
| 非功能 | 性能量化（QPS/RT/容量）；可用性（可容忍不可用时长）；合规审计要求 |
| 集成依赖 | 上下游系统与协议；同步/异步；对方不可用时本方表现 |
| 成功与边界 | 验收标准按AC规范可观察化（见下）；范围外声明（本次明确不做什么） |

> 量化指标用户答不出的，用 core 层性能规模经验做同类场景类比估算并标注假设，不空转追问（依据D8）

### 术语锐化（DDD统一语言，业界增补决议）

- 模糊/过载术语立即要求规范化："你说的'账户'是Customer还是User？这是两个概念"
- **用户陈述与代码矛盾时浮出确认**："代码取消的是整个订单，但你刚说支持部分取消——哪个对？"不静默采信任何一方
- 术语一旦解决即写入 Agent.md 术语表（不批量攒）；术语表只放词汇定义，不放实现细节

### 验收标准规范（AC，业界增补决议）

每条AC六要素：**场景 / 触发 / 预期可观察结果 / 禁止副作用 / 验证方式 / 优先级（必须/应该/可以）**

- 禁用模糊词："正确地/安全地/快速/直观/健壮"必须替换为可观察证据，或显式标记为人工评审判断
- 实现中AC因架构/平台约束无法满足：标 `[revised]` + 说明约束 + 调整范围或验证方式 + 只重报变更项——**不静默放弃或绕过**

### 事实与约束分离（业界增补决议）

- **技术事实**（系统今日行为、约定、契约）→ 自己查仓库，不问用户
- **业务约束**（业务规则/合规/SLA/定价/数据保留/优先级/目标用户）→ **永远不能从代码推断**，只能来自用户或产品工件；未知时记为"待确认假设"，绝不当作发现的事实
- **假设主动确认**（星枢案例复盘增补）：交付物含待确认假设时，交付说明必须附**假设清单**（编号+影响范围）并主动提请用户确认，不被动等待用户发起——假设过期未确认=设计带着未验证前提在走（星枢教训：口径假设存在5个版本才被确认）

### 文档格式规范（交付文档统一口径，用户偏好决议，2026-09-11）

- **统一 Markdown**：报告/调研/记录/设计文档等交付文档一律 Markdown 格式（.md），规范书写、任何查看器可正确渲染；不默认产出 Word/HTML（用户显式要求除外）
- **1-3 级标题配图标**：H1-H3 标题搭配适当 emoji 图标分节（如 📋/🎯/🔧），增强可扫读性；H4 及以下不加，防图标噪音（组件 README 的分节细则见 architecture#20，口径一致）
- **markdown-viewer 美化校对**：文档产出后经 markdown-viewer 渲染预览优化（排版/结构/图表）；环境未装该技能 → 按 tools 层**自动安装流程**处理（find-skills → belt），安装失败降级为文档机械自查并留痕"发现待办"（依据 tools#Skill组合策略 动态发现纪律）

### 文档任务机械自查（设计文档/README等结构性变更后，星枢案例复盘增补）

文档结构性变更（插入/删除章节、迁移内容、改编号）后**必须跑一遍机械自查**，与代码任务的九大类审查同地位：

- 章节编号连续无重复（插删章节后重点查）
- 交叉引用有效（"见 X.Y"/"见 ADR-xxx"指向真实存在）
- 代码围栏/mermaid 块闭合（数量为偶数）
- 上游/下游文档引用映射存在（引用产品文档 X.Y 节，需验证该节存在）
- 修订说明与实际变更一致（版本表声称"编号已顺延"，编号必须真的顺延）

### 需求产出物模板（复杂需求对齐确认后落地）

1. **背景与目标**：一句话业务价值 + 量化的成功指标
2. **用户场景**：角色 × 故事 × 频率
3. **功能清单**：P0必须 / P1应该 / P2可以，每项附一句验收标准
4. **非功能需求**：量化指标表（QPS / RT / 容量 / 可用性 / 合规）
5. **范围外声明**：明确不做的，防范围蔓延
6. **实现决策**（业界增补决议）：对齐过程中已定的实现选择（涉及模块/接口/schema/契约/技术澄清）记录成清单——**不写具体文件路径与代码片段**（易过期），原型产出的决策编码片段（状态机/schema）例外，内联并修剪到只剩决策信息
7. **测试接缝**（业界增补决议）：规格阶段确定从哪测——优先**已有接缝**、用**最高可用接缝**、接缝数量最少化（理想为1），与用户确认后再写实现
8. **开放问题**：编号 + 当前假设 + 待确认人；标注四类之一——**查证可解**（分身自查）/ **需对话**（拷问用户）/ **需原型**（造物验证）/ **需前置工作**（开通权限、准备数据后讨论才能继续）。**雾判据**：能精确表述的问题才入清单；表述不了的方向单独记录，不预切

> 小需求（单任务量级）不套模板：场景确认 + 验收标准即可，防流程官僚化（依据D2）

## 三、九大类审查清单（每个任务完成后过一遍）

> **黑盒审查机制（用户指令强化，决议）**：**一项任务做完之后，再审查；正式审查必须黑盒**——审查判断不能被开发过程上下文污染。"我的代码，我审核"不成立：同一会话带着全部设计讨论与决策理由，会顺着作者意图合理化，看不见作者盲区。必须由**不懂作者的人按规则审查**。

**执行方式**——在agent环境下，"不懂作者的人"= **无会话上下文的子代理**（不继承本会话历史，天然黑盒）：

- **输入白名单**（只给三样）：① 产出物本体（路径或内容）② 审查规则（本清单/文档机械自查/coding 层风格条款）③ 原始需求与AC
- **输入黑名单**（一律不给，给了就是污染）：设计讨论、决策理由、"为什么这么写"、作者自查结论、过程性备注——审查者只按产出本身与规则独立判断，不迁就作者意图
- **审查产出**：问题清单（按 D1 优先级排序）+ 双轴报告（规格轴/标准轴分别给结论）
- **处置闭环**：分身按报告修复；审查误报等争议项**提交用户裁决，不静默忽略**；修复后可复审
- **装备纪律**：审查子代理同样装备 tools 层"代码审查"组合skill（open-code-review等，未安装则按 tools 层自动安装流程处理）
- **环境降级**：子代理不可用时，退化为**新会话审查**（清空过程上下文、只给白名单三项重开审查），或请用户外部审查——同会话自查不能顶替黑盒

**自查与黑盒的关系**：作者九大类自查保留，但仅为黑盒审查前的**预清理**（快速过滤低级问题）；**质量结论以黑盒审查为准**。

> **双轴报告（业界增补决议）**：审查结论分两轴**分别报告、互不遮蔽**——**规格轴**（第1类：忠实实现需求？无范围蔓延？）与**标准轴**（第2-9类：质量/安全/性能/风格）。一轴通过不代表另一轴通过，禁止合并成单一结论。

> **审查热点聚焦（业界增补决议）**：架构审查/重构扫描前先 `git log` 圈近期变更热区，优先深挖热点（深模块收益=让未来变更更容易，权重给正在变的地方）；用户指定方向则直接用，**不全库扫描**（YAGNI）

### 1. 业务功能实现（规格轴）
- 需求对齐：完整覆盖需求与边界场景，无漏需求、无私自增删逻辑；状态机/枚举/流程跳转与设计一致
- 业务正确性：核心计算（金额/时间/统计/ID）防精度丢失、时区、溢出；多步骤业务防部分成功部分失败；出参/错误码符合约定
- 异常业务场景：非法输入、流程回滚、失败重试、权限拦截

### 2. 代码基础质量（标准轴）
- 命名语义清晰，常量统一管理；注释解释复杂算法与特殊规则，不写复述代码的无效注释
- 函数职责单一，避免巨型函数、多层嵌套；圈复杂度过高优先重构
- 重复逻辑抽公共；死代码及时清理
- 坏味道基线（Fowler精选，判断性提示而非硬违规，项目规范优先于基线）：神秘命名、重复代码、基本类型偏执（原始类型顶替领域概念）、数据泥团（同组字段总是结伴出行→该成类型了）、重复switch（同类型判断散落多处→多态/映射表）、霰弹式修改（一处变更散落多文件）、发散式修改（一个模块因多个无关原因被改）、投机泛化（为不存在的需求加抽象/参数/钩子）、中间人（只做转发不干活）、被拒绝的继承（继承了大半却不用→改组合）

### 3. 安全漏洞（重点）
- 外部入参全部校验（长度/类型/格式/范围），不信任前端
- 禁止拼接SQL，用预编译；防命令/模板注入
- 接口鉴权+越权检查；敏感数据存储加密、传输HTTPS、日志打码
- 第三方依赖排查已知漏洞；XSS/CSRF/文件上传校验/路径遍历

### 4. 性能与资源
- SQL：防全表扫描、缺索引、N+1；批量操作防循环访问DB；防大事务长事务；分页防深翻页
- 资源释放（流/连接）；大对象防OOM
- 并发：共享变量加锁、锁粒度防死锁、异步异常捕获
- 同步接口不做重逻辑，耗时操作异步化

### 5. 架构与可扩展
- 单一职责、开闭原则；分层不混乱
- 硬编码配置抽取；未来可能变更的逻辑预留扩展点
- 第三方调用超时/降级/熔断

### 6. 异常处理
- 不空捕获；区分业务异常与系统异常；异常不透传原始堆栈
- 关键错误打堆栈+上下文参数；重试防雪崩；幂等性

### 7. 兼容性与边界
- 边界值：null/空集合/0/最大最小值
- 时区、编码、跨环境差异；接口升级保持旧版本兼容

### 8. 可观测与可运维
- 关键节点埋日志、区分级别；核心业务埋监控告警
- 环境差异走配置；变更支持安全回滚，无不可逆数据变更

### 9. 测试
- 核心逻辑单测覆盖重点分支与异常场景
- 无硬编码测试数据/调试代码遗留正式版本

> **审查优先级：业务正确性 > 安全漏洞 > 异常健壮性 > 性能 > 代码可读性 > 架构可维护性**

## 四、调试纪律（疑难bug/性能劣化时，业界增补决议）

> 红线：**没有"红灯命令"禁止进入假设阶段**——先建一条能复现此bug的单条命令（快/确定性/可无人值守跑），90%的调试工作是让这条命令变红再变绿。对着代码空想理论，正是本纪律要防的失败模式。

1. **建反馈回路**：按优先级尝试——失败单测 / curl脚本 / CLI+fixture快照比对 / 无头浏览器脚本 / 回放捕获的trace / 最小系统harness（mock掉依赖只跑bug路径）/ fuzz循环 / git bisect自动化 / 新旧版本差分。建不成时（需特定环境/脱敏工件/生产插桩授权）→ 明确列出已试方案请用户提供，**不硬猜**
2. **复现+最小化**：先确认复现的是用户描述的那个症状（不是邻近的另一个错——错误的bug=错误的修复）；再逐项削减输入/调用/配置，只保留让红灯还亮的"承重"元素——最小化复现既缩小假设空间，也是将来的回归测试
3. **可证伪假设**：一次生成**3-5个排序假设**（只生成一个会锚定在首个想法上）；每个假设必须能说出预测——"若X是原因，改Y应消失/改Z应加重"；排序结果请用户过目再动手（用户一句"刚上线过#3"就能瞬间重排）
4. **带标签插桩**：一次只改一个变量，每个探针对应一个假设的预测；调试日志带统一前缀（如`[DEBUG-a4f2]`），结束时一次grep清零；优先断点/REPL而非撒日志；性能问题先测量（基线+profiler+执行计划）再动手，不用日志猜
5. **修复+回归测试**：在**正确的接缝**（真实触发bug的调用路径，而非够不着的浅层单测）把最小化复现转成失败测试→看它失败→修复→看它通过→用原始（未最小化）场景再跑一遍反馈回路。若找不到正确接缝，**这本身就是架构发现**——记录并升级，不要在错误的层面写假信心测试
6. **清理收尾**：原始复现不再复现；grep确认DEBUG标签清零；一次性脚本删除；**commit信息写明被证实的那个假设**——下一个调试者从这里学起
