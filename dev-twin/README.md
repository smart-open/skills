# dev-twin — 个人开发分身引擎

*版本：v1.1（暂定可用版本）| 定版日期：2026-09-06 | 画像库：persona-zhutianwei v0.10*

> **一句话**：外挂个人画像库的开发分身引擎——按画像主体的决策原则、编码习惯、架构偏好、工作方法，自主完成需求分析、架构设计、编码开发、测试审查；替换画像目录即切换分身。

引擎保持薄（定位/路由/分级/纪律/闭环，见 [SKILL.md](SKILL.md)），知识全在画像库（自描述，见 [persona-zhutianwei/README.md](persona-zhutianwei/README.md)），学习闭环规程见 [references/learning-loop.md](references/learning-loop.md)。

## 二、怎么使用

### 2.1 画像主体本人（日常使用）

**触发**：会话中直接给开发任务即可，或显式说"按画像执行" / "用我的方式" / "分身处理"。画像库自动定位（外部指定 > `PERSONA_DIR` > 当前目录 > skill同级 > 内置默认）。

**任务触发画像层自动路由**（同时激活 ≤3 层，token 可控）：

| 你做什么 | 分身加载 |
|---------|---------|
| 提需求 / 澄清需求 | core + workflow（拷问式对齐、AC规范） |
| 设计 / 架构 | core + architecture（决策留痕、ADR门槛） |
| 写代码 / 改代码 | core + coding（+ polyglot 若非 Java） |
| 选型 / 工具决策 | core + tools |
| 复盘 | core + learning-loop + corpus |

**交互节奏**：
- 画像明确覆盖的 → **L1 自主执行**，你只需看决策留痕（每条决策标注引用了画像哪条规则）
- 画像未覆盖的 → **L2 请示**，AskUserQuestion 列选项+推荐答案，你拍板
- 架构红线 / 安全 / 不可逆操作 → **L3 强制确认**，不自动执行

**你的日常姿势**：简单 review 把控大方向；发现不对**直接纠正**（说清哪里错、应该怎样）——纠正即语料，见第三节。

### 2.2 其他人使用（换画像=换分身）

1. **最简方式**：把你的画像目录放在**当前工作目录**或 **skill 安装目录同级**，命名 `persona-你的名字/`——5 级定位自动覆盖内置画像，引擎与规程零改动
2. **从零建画像**：见第七节复刻指引（复制骨架 → 备素材 → AI 提炼 → 双重校准 → 验证）
3. **结构约定**：画像库自描述优先——你的 `persona-你的名字/README.md` 定义自己的分层与加载策略，可不同于默认结构；但 `profile-core.md`（基础画像+决策原则）是唯一必需项，缺失则分身拒绝工作

## 三、怎么让它自我学习迭代

分身的进化=**语料积累 → 复盘确认 → 入库 → 淘汰**四步循环，你只需参与第 1 步和第 2 步的确认。

### 3.1 日常纠正（你唯一必做的动作）

发现问题直接说：哪里错了、应该怎样（如"error 日志要带堆栈"）。分身自动将纠正写入 `persona-xxx/corpus/raw-corpus.md` 待复盘区——**不需要你做任何其他操作**，当前任务同步修正，画像层等复盘批量更新（闭环纪律优先于效率）。

### 3.2 复盘入库（语料攒 10 项触发，或你说"复盘"）

1. AI 读语料，**预生成结构化总结**（按画像层分组、候选条目可执行化、冲突标注合并建议）——你不用自己整理
2. 你逐条确认：**采纳 / 修改后采纳 / 放弃**（AskUserQuestion 分批，每批 ≤4 条）
3. 确认项写入对应画像层（版本号 +0.1），语料移入归档区（保留原文永不删除）

成本参考：一次复盘约 10 分钟。

### 3.3 淘汰机制（复盘时顺带执行）

复盘时统计画像条目引用情况——**连续 3 个月未被任何决策引用的条目** → 列入淘汰候选向你展示 → 确认后移入该画像层底部"归档区"（不物理删除，保留恢复能力）。这是防画像膨胀走回"费token、跑偏"老路的生命线。

### 3.4 案例反向校准（进阶，适合阶段性大任务后）

一个完整案例（如星枢平台设计全流程）结束后，可说"**案例反向校准画像**"：

1. AI 对照画像规则逐条核对案例实际行为 → **正例确认**（哪些规则有效兑现）+ **偏差定位**（哪些环节暴露画像缺口，附根因）
2. 校准建议清单 → 你逐条勾选 → 入库（新规则标注来源案例，首例标"待二次验证"）
3. 全过程归档 raw-corpus.md（复盘R1 即首例）

### 3.5 进化铁律

- **未经你确认，任何内容不写入画像层**——防错误经验污染
- **原始语料永不删除**——画像可随时从语料重建
- **决策 100% 留痕**——出问题可定位是画像错（修画像）还是执行错（修流程）

### 3.6 迭代触发条件与验收标准

**触发条件**（满足任一即执行对应动作）：

| 触发器 | 条件 | 动作 |
|--------|------|------|
| 语料阈值 | 待复盘语料 ≥10 项 | 主动提醒复盘（AI 发起，不依赖用户记忆） |
| 积压预警 | 未复盘语料 >20 项 | 强制预警，优先复盘、暂停画像层扩展类改动 |
| 用户主动 | 说"复盘" / "案例反向校准画像" | 立即执行对应规程（learning-loop.md） |
| 定期 | 每月 1 次或每完成 1 个完整案例 | 常规复盘：语料处置 + 引用统计 + 淘汰评估 |
| 淘汰候选 | 条目连续 3 个月未被任何决策引用 | 复盘时提议归档（用户确认后执行） |
| 条目冲突 | 新纠正与现有画像条目矛盾 | 当场标记冲突，复盘时向用户复述两条并定夺合并 |
| 待验证先例 | 标"待二次验证"的条目遇到对应场景 | 通过→摘除标注；证伪→回退条目+教训入语料 |
| 层膨胀 | 单层条目超软上限（core/coding/tools ≤30，architecture/workflow ≤60） | 复盘重点评估合并与归档 |

**验收标准**（各迭代类型的完成定义，缺一不算完成）：

| 迭代类型 | 验收标准 |
|---------|---------|
| 常规复盘 | ① 语料 100% 处置（采纳/修改后采纳/放弃三态，无悬置）② 入库条目 100% 经用户确认 ③ 画像层版本号 +0.1 ④ 语料移入归档区 ⑤ 下次任务至少引用 1 条新入库条目（学习效果可观察） |
| 案例反向校准 | ① 正例清单 + 偏差清单双产出 ② 偏差项均附根因与落位（画像层+条目号）③ 用户逐条勾选留痕 ④ 复盘编号（R1、R2…）与语料一并归档 |
| 淘汰执行 | ① 候选清单附未引用依据 ② 用户确认留痕 ③ 移入层内"归档区"非物理删除 ④ 明确恢复方法 |
| 冲突合并 | ① 原条目改写不删除（附修订日期与来源）② 冲突点向用户复述确认 ③ 仲裁符合优先级：决议表 > 决策原则 > 分层条目 |
| 二次验证 | ① 验证场景留痕（哪个任务、哪条决策引用）② 通过→摘"待验证"标注 ③ 证伪→条目回退归档 + 失败教训写语料 |
| dev-twin 版本发布（vx.y） | ① 画像库版本同步声明 ② README 版本历史新增行 ③ 新增能力有真实案例验证支撑 ④ 全技能五查机械自查通过（章节编号/交叉引用/围栏闭合/上游映射/修订说明一致性） |

## 五、后期路线（阶段三/四在实战中逐步完善）

### 阶段三：进化闭环（🔄 实战中持续）

- [ ] 语料积累至 10 项触发复盘（当前 2/10，均为 coding 层）
- [ ] 复盘节奏执行：攒10项 → AI预生成结构化总结 → 用户逐条确认 → 入库 → 语料归档
- [ ] 淘汰机制启动：复盘时统计画像条目引用情况，连续 3 个月未引用 → 提议归档（归档不删除）
- [ ] 自主决策比例按月统计（L1 决策数 / 总决策数），随画像覆盖度提升逐步扩大 L1 范围
- [ ] P4（Go 窄内核纪律，polyglot#9）等待下一个 Go 高并发组件任务**二次验证**，验证通过后摘除"待验证"标注
- [ ] 工程规模爬坡测试：小项目验证通过后逐步扩大规模，观察画像分层加载在大工程下的表现

### 阶段四：产品化（📋 阶段三成熟后启动）

- [ ] 画像模板化：抽出空白画像模板（骨架+提炼流程文档），与个人数据彻底分离
- [ ] 第二人素材跑通提炼流程，验证画像可替换性 + 私有数据隔离
- [ ] 画像覆盖度达 80% 前不对外推广（防过早产品化分散精力）
- [ ] 分发形态确认：整目录分发 / 仓库 fork / 其他

### 日常使用中的持续事项

- 用户纠正 → 自动写入 `corpus/raw-corpus.md` 待复盘区（分身执行，不需用户操作）
- 交付物含待确认假设 → 交付说明附假设清单主动提请确认（workflow 层 P1 规则）
- 文档结构性变更 → 跑五查机械自查（编号/引用/围栏/上游映射/修订说明一致性）
