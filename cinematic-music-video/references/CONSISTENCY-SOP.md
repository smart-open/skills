# 强一致性 SOP：人物 / 画面 / 配饰

> 来源：《秦淮灯下影》全周期制作实测（2026-09-25 ~ 10-03，77 镜双画幅 + 11 轮定妆迭代 + 68 镜逐镜 i2i 修正 + 4 轮返工 + 视频全量重拍 + 双版成片交付），并整合此前五部 MV 的一致性教训。
> 与 `HARDENING.md` 的关系：那份是"出问题怎么判、怎么修"的坑位手册；这份是"从第一步就让它不出问题"的标准作业流程。两份配合使用。
> 主技能 `assets/` 目录下有两类配套脚本：
> **补丁脚本**（`patch-refs.js` / `plan-resilient.js`，用 `node -r` 预加载，**必须传绝对路径**，坑位 7）；
> **QA 工具**（`montage.js` 拼图 / `shot-times.js` 抽帧时刻 / `crop-zoom.js` 定点裁切 / `rehost.js` 换公网 URL，直接 `node` 运行，需设 `NODE_PATH` 以解析 sharp）。

## 0. 一致性的七条线 —— 先分清谁负责什么

| 一致性线 | 保障机制 | 谁来验收 |
|---|---|---|
| **脸** | 角色设定表 → 身份锁 → 面部锚点 + `compareIdentity` 门禁 | 门禁给线索，**人眼裁决**（坑位 46） |
| **地点/画面** | `scenes[]` 锚点图 + 构图/姿态/地点文字锁 | 门禁**看不见构图错误**，接触表目检 |
| **服装** | **角度匹配的全身参考图** + `wardrobe_layers` 逐层注入 + refGuard 单句守卫 | 与设定表并排对照（门禁对服装不敏感，坑位 36） |
| **视角/角度** | `ref_body_<angle>` 多图 i2i + storyboard `characters_view` 自动匹配（§3.14） | 目检——**T2I-first 下视角指令会静默失效** |
| **画面孤立** | **`SCRUB` 场景级清「人」+ `ISOLATION` 紧贴场景文案 + 空镜 `NO_PEOPLE`**（§3.15） | `dbg-people.js` 扫文案 + **全量成品人眼巡检** |
| **配饰/道具** | 识别级文字锁（颜色+材质+几何朝向+标志装饰+携带方式） | **只能人眼**——门禁不判道具（坑位 59） |
| **参考图集自身** | 六视角各过一遍 canon 自检 + `mirror-refs.js` md5 校验（§3.16） | **逐视角人眼目检**——一张坏图污染覆盖它的全部镜头 |

铁律：**门禁只回答它被设计的问题**（是不是同一个人 / 有没有字）。
构图、道具、服装方向、媒介质感，全靠"参考图组合管理 + 目检"补位。
**「画面里有没有多余的人」门禁答不了** —— 场景文案点名要的 vendor / guest / 路人会被忠实画出来，
必须在文案层清洗（§3.15），并做全量成品巡检。

## 1. 基准先行：定妆图闸门制（烧大额度之前必须签字）

设定表和关键帧是全片额度的决定性上游，基准错一轮 = 下游全部重画。流程：

```
设定表多候选 → 用户目检选号 → 【签字】→ 身份锁定（_source="manual"/"storyboard"）
→ 关键帧批量生成 → 接触表目检 → 用户【签字"统一"】→ 才进视频阶段
```

- **定妆迭代用 i2i 锚定，不用 t2i 重抽**（坑位 69）：整体已对、只调局部（口型深浅/体型/发型）时，
  以当前最佳图为基底 `images:[公网URL]` + "只改 X、其余全部锁定"。t2i 重抽方差极大。
- **迭代不满意就回退**：用户多次在 4-6 轮迭代后说"还是用最初的"——保留每个版本的归档目录，
  回退是正常操作不是失败。
- **身份锁防覆盖**：任何 `--force` 重跑前先查 `character_lock.json` 的 `_source`
  （坑位 6/43）；`vision-from-sheet` 来源的锁，服装/体型字段必须与 `storyboard.character.params`
  逐字段核对（反读读错颜色是高发区）。
- **用户给参考图 = 最高优先级真源**。服饰细节必须逐件向用户确认方向
  （实测"白鞋红带"与参考图"红鞋白带"写反且从未被发现）。

## 2. 逐镜关键帧生产：生成与判定解耦

这是整条流水线最重要的架构决策（在评分 bug 事故中证明了价值）：

1. **生成侧只管出图**：每镜最多 N 候选，落盘 `shot_SXX.png` + `.url` sidecar。
2. **判定侧独立评审**：`chatVision` 缓存评审结果（`.vision_cache/`），与生成解耦。
3. 收益：判分逻辑有 bug / 门禁要改判据时，**用已有候选零额度重审**（rescue 模式），
   而不是重烧生图额度。

### 2.1 评审提示词设计（两条铁律）

**铁律 A：判据布尔化，别依赖自报分数。**
让模型逐项回答 yes/no（披帛在不在 / 水滴口在不在 / 长度对不对 / 金绣 / 构图冻结），
分数 `VERDICT: 0-100` 只做参考。布尔判据稳定，分数是噪声（坑位 53：同一张图两次能差 60 分）。

**铁律 B：解析按行号为主、关键词兜底。**
评审模型经常剥掉关键词头只回 `1) yes / 2) yes`（坑位 70 实测，4 候选全部因此误判 -1 分）。
解析器写法：

```js
const byNo = (n, kw) => (lines.find(l => new RegExp("^\\s*" + n + "[).\\s：:]").test(l)) || "") || get(kw);
```

VERDICT 分数解析要先剥行号前缀再抓数字，`PASS` 无数字按 90 处理。

### 2.2 长度/姿态类判据要给几何语言

"水滴口不是 2/3 胸宽"这类判断，对模型用抽象比例词（exactly two-thirds）服从性差；
改几何描述："WIDTH spans MOST of her chest width (about three-quarters), vertical length from
collar base down to the BOTTOM of her bust — not beyond"。

## 3. 局部修正 SOP：逐镜 i2i 定向编辑

逐镜 t2i 重抽"回缩软化"（每镜随机退回保守默认）三次复现后，换打法：
**以每张已验收关键帧为基底做 i2i 定向修正**。68/68 达标的完整打法：

### 3.1 基底与跳数

- **单跳原则**：以最佳候选图为基底，一次只改一个部位。i2i 跳数越多脸越差（糊 + 卡通化）。
- 全量批量修正用脚本驱动：`状态文件断点续跑（{shots:{id:{status,best,bestScore}}}）`
  + 多候选（每镜最多 4）+ 布尔门禁 + 不过自动换候选重试。
- 覆写部署时**用候选自身的 `.url`**，别拿旧基底 url 覆盖（会让视频阶段用错图）。

### 3.2 提示词模板（冷冻式）

```
LOCAL RETOUCH of this exact image. HARD REQUIREMENT ZERO — <最易丢的配饰/服装件，放最前>：
she MUST keep ... exactly as in the source. NEVER remove it; if it faded in the source, render it MORE visible.
ONE edit only — <几何化的修改指令>.
FROZEN, keep EXACTLY as in the source: <逐项点名：pose / face / hairstyle / 场景元素 / 灯光 / framing>.
Everything else pixel-identical.
```

要点：

- **配饰硬锁放首位**：夜景深色纱质配饰（披帛/纱巾）会被模型"正常化"掉，
  四候选全丢过——列为 HARD REQUIREMENT ZERO + "render it MORE visible" 后才锁住。
- **冻结项逐项点名**，一个词都不省（face / pose / boat / lanterns / framing …）。
- **改动指令用几何语言**（见 2.2），边界只许肯定式描述，别写 "must NOT run past X"
  这类负向边界——实测会把整套设计一起压回保守默认（坑位 69）。

### 3.3 比例参考双图 i2i

用户说"太长/太宽，参考别镜"时：`images: [基底url, 参考url]`，
提示词声明 "The SECOND image is only a PROPORTION/SHAPE REFERENCE — match the <部位> of the
woman in the second image"。实测一次命中率显著高于纯文字描述比例。

### 3.4 身材与安全措辞（t2i / i2i 分开记）

| 场景 | 有效措辞 | 无效/危险措辞 |
|---|---|---|
| t2i 定体型 | 结构化裁剪语言：`curvaceous full-figured hourglass figure`、`deep V-shaped keyhole opening from the collar down to the mid-chest, edges trimmed with piping` | `deep plunging ... cleavage`（触发整句服装被吞，回退保守默认，坑位 68） |
| i2i 调体型 | 相对量：`make her bust ONE FULL CUP SIZE LARGER than in the source image` + 视觉描述 | 绝对罩杯字母（`full C-cup`）会被软化成 modest |
| 真人感 | `natural skin texture with visible pores`、`refined classical Chinese beauty` | `real actress` / `film star` + 身体描述 → **确定性 400**；`gongbi-painting` / `porcelain skin` → 全 CG |
| 内容安全 | 阈值随时间收紧：上周能过的措辞本周 400。被拦就**软化措辞**（"completely filling the open teardrop neckline" 替代身体部位直述），不是重试 | — |

### 3.5 特例镜不自动部署

机器判过 ≠ 用户认可（S41 首修 92 分被驳、S16 卡通 92 分放行）。部署纪律：

- 批量脚本**永不自动覆写**用户在意的特例镜；产出候选 → `present_files` 交目检。
- 用户回复"选择N / 可以"→ `cp 候选.png(+.url) → shot_SXX.png(+.url)` 部署。
- 恢复备份后 `.url` 缺失 → **首选：data URI 边车**——把 `data:image/png;base64,<...>` 直接写进
  `shot_SXX.png.url`，videos.js 零改动，视频 API 的 `first_frame` 接受 base64 data URI（约 9MB
  实测通过，2026-09 验证），像素零损失。**兜底：克隆式 i2i**——本地图转 data URI 为源 +
  零改动复刻提示词让 API 返回新 URL 重新托管；注意克隆会重渲染整图，实测漂移可能很大
  （服饰位置改变、手消失），克隆后必须局部对比核验，不可直接部署。

### 3.6 双人病与两步法（t2i 底图 → 换脸回贴）——2026-09 全量重掷期确诊

**症状**：单人流镜生成出「两个穿同款旗袍的女人」（一瘦一胖/一分身）；
特写镜（眼/手/颈/指节）被画成全身站姿；构图与分镜完全无关。

**根病（四轮盲掷实证）**：
- 图像 API 对「脸参考 + 身体参考」**双人物参考 i2i 的 prompt 遵循度极差**——模型把两张
  参考图直接画成两个人，HEAD 强锁 / 正向陈述 / 防 CG 锁均无效（prompt 层面无解）。
- data URI 参考边车会加剧 prompt 失效与 CG 断裂；**参考图一律用公网 URL 边车**。
- `--no-scenes` 丢场景锚点 → 模型另起炉灶（画面场景漂移）。探针单镜跑正常、批量同参
  数跑翻车时，先查 `--no-scenes` 与边车类型组合。
- 局部镜（手/颈/指节等）挂人物参考 = 被拽成完整人形；**必须走 PART_SHOTS 预载
  （globalThis.CMV_PART_SHOTS）不挂人物参考**——实测这类镜纯 t2i 构图一次命中。
- QA 门禁只查脸像+数人，**不校验构图 vs 分镜**——「通过」≠「内容对」，批量出图后必须
  拼总览图人眼逐镜比对分镜描述。

**两步法（根治，已验证）**：
1. **Step A — t2i 纯文字底图**：不挂任何参考图，prompt=分镜场景+人物描述+35mm 实拍锁，
   构图/prompt 遵循度满格。
2. **Step B — 换身 i2i（v3，权威全归锚点）**：Picture 1=清痣 ref_body_front 身份锚点、Picture 2=底图；
   措辞「Replace the woman in Picture 2 with the EXACT same woman as in Picture 1. Take from
   Picture 1: her face, hairstyle and hair ornaments, and her outfit（逐件列服装）; take from
   Picture 2 ONLY: composition, camera framing, angle, pose, background, lighting, film grain」。
   **只换脸不换装的措辞会导致服装随底图漂移**（v2 教训：t2i 底图无服装锚定，每张底图各画各的
   衣服），服装/发型权威必须显式归锚点图。**服装微观一致性（刺绣纹样/数量/位置）仅靠参考图
   仍会被模型自由重绘——必须再叠文字显式规格锁**（v4 教训：从锚点图人工读出规格，如「金牡丹
   仅在胸口水滴口两侧对称各一朵，领口红滚边红盘扣，裙身素黑无花」，逐句写进换脸/align 措辞，
   全镜统一率大幅提升）。局部特写镜（手/颈/指节）服装免一致性，不纳入换装轮。
3. **免换脸镜与 align 变体**：背影/远景（脸不可见但有服装）→ **align 变体**：「Reproduce
   Picture 2 EXACTLY … with ONE change only: the woman's outfit, hairstyle and hair ornaments
   must exactly match Picture 1」。纯局部特写（手/指节）、航拍微小人物 → Step A 底图即候选。
4. 产出候选 → 总览拼图 → 用户圈改/签字 → 部署，绝不自动覆写。

### 3.7 补丁轮的天花板与「文字权威 + 仅换脸」重建架构（v6）——2026-09 逆向教训

**症状**：在两步法上连续打补丁（v2 服装 → v3 权威归锚点 → v4 刺绣文字规格 → v5 描边擦除），
每轮只修一个点却弄坏另一个点——最终用户判定「越改越乱：水滴口和胸部乱了、人脸也不一致」。

**根因（三条）**：
1. **换脸步骤里只要出现任何服装描述，模型就会重绘那片区域**。v3/v4/v5 都在 Step B 里写服装
   （甚至写「把底图裙身上的花擦掉」），于是每一轮都把领口/水滴口/胸口重新画一遍，形状逐轮漂移。
2. **文字规格与签字定妆图冲突时模型两头不靠**。v4 按分镜文字写「水滴口两侧胸口各一朵」，
   而签字定妆图实际是「金牡丹在双肩蕾丝上各一朵、水滴口窄约 1/5 胸宽」，模型把花撒到满身。
3. **T2I 底图自身带错**（底图裙身已有散布花纹），i2i 会优先保留底图服装 → 再精确的措辞也压不住。

**v6 架构（一次性重建，不再打补丁）**：
1. **Step A — 纯文字 T2I 底图，服装规格只保留「唯一一份」权威文字**（来源 = 分镜 character
   params + 签字定妆图），逐镜一字不差地拼接 → 跨镜一致由文字保证，不靠模型自觉。
   必写硬约束（缺一条就会跑偏）：
   - 旗袍**永远素黑，即使淋湿也不发白**（否则雨镜里会被画成米白/象牙色）；
   - 披帛**永远双肩前垂两片**（否则退化成身后红柱）；
   - 水滴口**宽**（领口底起、圆底与**胸底线齐平**、最宽约 **3/4 胸宽**、红滚边一圈、每镜同尺寸），
     胸围为**丰满 D 罩杯 + 深乳沟**——**以用户 2026-09-30 最终签字的效果图为准**，
     分镜文字若与之冲突（如写成「窄口 1/5 胸宽」或 2/3）一律弃用；
   - 刺绣位置写清层位（肩/胸/领），并补「肩线以下素黑无花」。
2. **Step B — 仅换脸 i2i**：Picture 1=签字 ref_face、Picture 2=底图；措辞只写「换面部特征+发型」，
   并显式加**禁止重绘条款**：「Do NOT repaint, reshape, restyle or lighten her clothing, neckline,
   keyhole or chest」→ 胸口永不被触碰，杜绝累积污染。
3. **特写镜走单图 i2i**（只挂 ref_face + 文字构图），不走两步——横幅画幅下 t2i 直出特写会拉长脸。
4. **免挂参考的镜**：局部特写（手/鞋/影子、`CMV_PART_SHOTS`）与空镜 → 纯文字 T2I，直接采用，
   既不换脸也不换装。

**闸门**：先跑 4 镜试点（含 1 特写 + 1 中景 + 1 远景 + 1 局部）自检 → 通过才全量；否则只赔 8 张图。

### 3.8 定妆效果图的生成法 + 「锚点整体复制」变体（v9）——2026-09-30

**A. 定妆效果图（用户只认一张权威形象时）**
两条路线，**优先走 B**：
- **Route B（身份保真最好）= 编辑已签字的定妆图**：`Picture 1 = 签字的定妆图`，措辞
  「Reproduce Picture 1 **EXACTLY** … with **ONLY these N changes**: (1) 去痣 / (2) 放大水滴口 …
  (3) 胸部更丰满 …」，并逐条列出不变项（刺绣位置/蕾丝袖/领口/披帛/耳饰/唇色）。
  实测同一张图做局部编辑，五官保真度远高于「重新 T2I + 换脸」。
- **Route A（备选）= T2I 正视图 + 仅换脸**：脸更容易偏离签字脸，仅在 B 路线跑不出时用。

**B. 「锚点整体复制」变体（Z 模式，`CMV_PLAIN_BASE=1 CMV_FULL_COPY=1`）**
当锚点图（定妆效果图）已被用户签字，且用户反复抱怨服装不一致时的**最强一致化手段**：
1. **Step A 只画素黑旗袍**：服装文字里**完全删掉刺绣描述**，改成「完全素黑、无任何刺绣/花纹」
   （脚本里用 `WARDROBE_PLAIN` 正则替换 WARDROBE 的刺绣段）→ 底图不可能把花画错位置。
2. **Step B 整体复制**：`Picture 1 = 签字定妆图`、`Picture 2 = 底图`，措辞从「仅换脸」升级为
   **脸 + 发型 + 服装 + 刺绣全部照 Picture 1 复刻**，同时显式保住 Picture 2 的**姿态/机位/构图/背景/
   灯光/颗粒**（「KEEP FROM PICTURE 2 …」）。
3. 实测效果：**水滴口形状、披帛形态、脸**跨镜高度一致（这是 X 模式做不到的）。
4. **残留缺陷（必须知道）**：模型仍会在约半数镜头**额外自增一组花簇**（多落在腰/裙摆/下摆）。
   已试过四轮措辞压制（计数法「exactly TWO flowers」、去掉 peony/flower 字样、前置 CRITICAL 行）
   **均只能缓解不能根除** → 战略上接受，交给总览审图圈改单镜重掷，不要在措辞上无限迭代。

**C. 面部锁 vs 服装锁互斥（重要）**
若在成品上**再补一次「仅换脸」**，模型会**重绘胸口**（实测水滴口被改小）→ 想锁脸就保不住服装，
反之亦然。**一次 i2i 只锁一件事**；两件都要锁时，走 B 的「整体复制」而不是分两轮。

**D. 参考图去痣的坑**
用 i2i「去掉参考图上的痣」会把**整张脸重画**（CG 化、五官变样）——这种「去痣版」**不能当身份锚点**。
正确做法：重新出一张无痣的**签字效果图**，用它替换 `ref_face.png`（原件备份到
`_qa/review/ref_face_orig_backup_<date>/`），并在脚本里同步换掉 `.url` 边车。

### 3.9 细节级一致性的天花板与「局部化重绘」架构（v10）——2026-09-30

**先认清 API 的硬边界**：`agnes-image-2.5-flash` 的 `/v1/images/generations` 只接受
`prompt + size + ratio + extra_body.image[]`——**没有 mask、没有 negative、没有 strength、没有 seed、没有 ControlNet**。
所以「遮罩重绘」在 API 层不存在，一切约束只能落在**文字 + 参考图**上。

**根因（为什么全局提示词永远调不好一朵花）**

| # | 机制 | 证据 |
|---|---|---|
| 1 | **参考图传结构，结构优先于文字** | HARDENING 坑位 4 实测矩阵；`assets/patch-refs.js` 已固化 |
| 2 | **细节分辨率衰减（决定性）** | 全图 i2i 时锚点刺绣被缩到几十像素，模型分辨不出 → 按先验重绘。Impact Pack 原文：*"a face occupying 80×80 pixels of a 1024×1024 render gets 80×80 pixels' worth of the model's attention, so it comes out mush no matter how good your model is"* |
| 3 | 装饰母题是**高熵属性** | 文字只给语义位置不给像素位置，每张都在重掷 |
| 4 | 文字规格与锚点图隐性冲突 | 文字写「well below the collarbone」而锚点花更靠上 → 模型两头不靠 |
| 5 | 否定式措辞反噬 | 写「不要在裙摆加花」＝把「花」这个 token 喂给模型 |
| 6 | 多图 i2i 注意力稀释 | 脸参考 + 底图同时挂 |
| 7 | 定妆锚点是半身像不是纯脸特写 | 与 HARDENING 坑位 8 同源：锚点自带服装/构图结构 |

**GitHub 调研结论（该领域怎么做）**

- `HVision-NKU/StoryDiffusion`、`ConsiStory`：跨图一致性靠**跨图自注意力**，训练无关——但需要本地 SDXL，API 用不了。
- `IP-Adapter` / `tencentarc/PhotoMaker` / `InstantID` / `PuLID`：只解决**脸的身份**，不管服装细节。
- `ali-vilab/AnyDoor`（CVPR2024）：mask 内重绘、**mask 外像素比特级不变**。启发：**局部重绘 + 原样回贴**。
- `ltdrdata/ComfyUI-Impact-Pack` 的 `Detailer(SEGS)` / `FaceDetailer`（＝ A1111 的 ADetailer）：
  **detect → crop → upscale 到 guide_size → 局部 img2img → feather 回贴**，denoise 0.4~0.5。
  这是唯一能在「无 mask API」下等价复刻的路线。
- `IDM-VTON` / `OOTDiffusion` / `DressCode`：整件服装迁移，对我们（只差一朵花）过重。

**v10 架构：局部化换装（`_qa/region-swap.js`，已试点验证）**

```
Step1  视觉模型定位胸口框：chest（水滴口 + 两侧刺绣的最小外接矩形）
Step2  补花 pass：紧贴黑布面的小框（1.18× 胸宽）高分辨率重绘；参考 = 定妆图胸口裁片（1024²）
Step3  回贴：把补丁与底图做逐通道色彩统计对齐 → 用「金色通道」门控 alpha → 只把新增的金色像素贴上去
Step4  余花清理（按需）：对游离在框外的余花做小框定向擦除
```

**五条硬规则（全部踩过坑）**

1. **补花框要「紧贴黑布面」**：框一旦切到背景/红披帛，重绘后的背景与原图不一致 → 可见接缝。
   取 1.18× 胸宽、居中于水滴口，让框基本落在黑色绸面上。（1.5× 仍会切到披帛，实测出接缝。）
2. **回贴必须「只贴金色像素」，不能整块替换**：整块替换（哪怕羽化 10% + 色彩对齐）在脖子/背景处仍留可见矩形边。
   用金色通道门控（判据见下节）：黑布 → 0（保留原图），金牡丹 → 1（贴上），**红披帛色相 ≈ 0° → 自动被排除**。
   这是「贴花」而非「换区」，从结构上就不可能有接缝。
3. **擦花也必须走门控**：全画幅擦花 pass 的输出漂移极大——实测模型把「抹掉刺绣」泛化成「抹掉装饰」，
   **把红披帛整片擦掉、水滴口也变了形**。若整幅回贴必然毁脸。
   正确做法是「门控擦花」：只替换「原图本身是金色 **且** 擦花前后亮度差足够大」的像素 →
   漂移被锁死在原刺绣像素上，脸/水滴口/披帛一个像素都不动，**并天然把 chest 框外的余花（腰/裙摆）一起清掉**。
   同时在 `ERASE_SPEC` 里显式声明「红披帛不是装饰，别擦」双保险。
4. **也不要用「整件旗袍矩形框」擦花**：小框裁切重绘会触发模型**重新构图**（水滴口被吃掉、画面被推近），回贴就是一条暗带。
   （门控擦花对重构图不敏感——只取原刺绣位置的黑布像素；但仍以全画幅为准，避免框边效应。）
5. **补花框的参考必须是「胸口裁片」而不是整张定妆图**：整张定妆图里刺绣只占几十像素（根因 2 重现）；
   裁成 1024 方图后刺绣占满画面，转移才算数。

**门控的两套判据（本轮最大教训，两个方向都踩过坑）**

| 用途 | 判据 | 为什么必须是这个松紧 |
|---|---|---|
| 擦花 `erase` | **色相 33°~66° + 饱和度 > 0.20**，且 `\|Δlum\| > 16` | **严格**。判宽了会把皮肤高光当金色去替换 → **脸上长出米色花瓣状斑块**（实测 S06/S18/S22/S31 全中）；`Δlum` 判据再兜一层底：擦花前后亮度没变说明本来就不是刺绣 |
| 补花 `decal` | **`min(R,G) − B > 14`** 且 **`\|R−G\| < 70`** | **宽松**。patch 里模型新画的牡丹是**淡香槟金**，饱和度常低于 0.20，套用严格色相门控会把整朵花砍掉（表现为「只贴上一朵、还很淡」；框内只有黑绸/花/胸沟/红滚边，误判胸沟贴上去的还是皮肤，无害） |

**配套铁律：回贴时绝不做逐通道 std 色彩缩放。** 框内的红披帛会把金花「染红」，染红后又被金色门控判掉——
这正是「右胸那朵花消失 + 原地留下一块暗红」的根因。只做 ±20 以内的**全局亮度偏移**即可。

**验证工具**：`node _qa/diff.js before.png after.png out.png` 出 5× 差异热图，
确认「改动是否被严格限制在目标区域」。**合格线：热图只有胸口一小块亮，脸/披帛/背景必须全黑。**

**提示词工程化写法（配合上述架构）**

- 位置**不要用坐标、不要堆形容词**，用**参照物**：「紧贴水滴口的左/右外缘」「竖向中心在开口最宽处」。
- 尺寸用**相对比较**而不是绝对量：「THE SAME SIZE … AS IN PICTURE 1, not smaller and not lower」。
- 否定句**只保留最关键的 1–2 条**（如「除这两朵外的整件裙身素黑」），不要罗列 6 条「不要在哪里加花」。
- 局部重绘提示词**首句锁死「画面其余部分一律不变」**（姿态/机位/背景/光线/肤色），否则模型顺手重构。

**闸门**：先跑 2–3 镜试点（1 全身 + 1 近景）目检接缝与花位 → 通过再全量。

**已知残留**：`chest` 框外的余花（腰/裙摆）不会被自动清掉，需按规则 4 逐个瞄准擦除。全量时先跑一遍、总览圈出余花镜，再批量定向擦除。

### 3.10 「完全确定性后处理」架构（v12–v15）——2026-10-01

**为什么还要再换一次架构**：v10/v11 的局部重绘（局部 i2i + 门控回贴）虽然把接缝问题解决了，但
**花本身仍是模型画的** —— 位置/大小/形态每一镜都在重掷，实测出现「偏黄、偏小、多一朵、位置偏高」。
只要花是模型产物，一致性就没有上界。v12 起把这一段彻底移出模型：

```
① 擦花（程序化，确定性）  把目标镜原图里的刺绣用结构判据找出来 → 用周围真实绸面纹理填掉
② 盖章（程序化，确定性）  把 B1 定妆图抠出的两朵牡丹精灵，按「开口宽度」等比缩放，
                          精灵的开口左上角对齐目标镜的开口左上角 → 贴上去
```

花的位置/尺寸/颜色 100% 由 B1 带过来，与模型无关 → **同一套参数在 77 镜上结果完全一致**。
代价是「擦花的自然度」，但这块会被盖章覆盖大半，只剩边缘可见 → 可接受。

**① 开口定位（一切几何的基准）**

- 主判据用**皮肤连通域**，不用红滚边环：滚边是细环，断裂/被花咬掉时会变形；皮肤块稳定得多。
  过滤 `area>1200 && fill>=0.45 && 0.75 <= bh/bw <= 3.0`，取面积最大。
- **两级搜索**：先全框找；失败才退到「下 65%」。有些机位脖子皮肤与开口连成一块，整块长宽比超限会被误拒
  （9:16 S11 实测）。直接砍到下半区会把好镜头的开口上沿切掉，所以只在全框失败时才回退。
- 兜底：滚边环检测（`findRing`）+ 按 B1 实测比例内缩 `PIPING_INSET{l:0.062,r:0.062,t:0.061,b:0.042}`。
- ⚠ 自动检测与所有辅助脚本（`zoomq.js`/`zoomf.js`）**必须共用同一套两级逻辑**，
  否则裁切窗与掩膜对不上，会看着像"擦歪了"（踩过）。

**② 擦花：结构判据链（顺序不能换）**

| 步 | 做什么 | 为什么 |
|---|---|---|
| A | 绸面 = `L<95 && sat<0.42`；1/8 尺度膨胀封缝、并**强制封住开口矩形** | 开口不封会顺脖子连到背景，贴开口的花会被判成"外部" |
| B | 从画幅边界漫水 = 外部 → `body = 实心 ∪ 非外部`；**只保留与开口同属一块的主连通域** | 桥洞背景墙也能满足"暗且低饱和"，不取主连通域会整幅蔓延 |
| C | 皮肤区从开口沿 `isSkin` 连通扩张 → `skinR` | 脖子/脸与开口是连续皮肤 |
| D | 候选花 = `body ∧ L>=100 ∧ ¬开口外扩框 ∧ ¬(开口顶线以上的皮肤)` | 不用"比局部基准亮 40"——大朵花瓣自身就撑满基准，必漏 |
| E | 排除 `redBig`（大块红 = 披帛/滚边/盘扣）与 `warmBig`（大块暖色，含披帛暗部 sat 0.25~0.45） | 披帛亮褶 `L` 也能到 100+，不排会在披帛内缘爬出一条细长假掩膜（擦完是一道深缝） |
| F | 边界须邻接**干净布料**（黑绸 ∪ 红披帛 ∪ 暖色）≥ 0.25，且贴 `body` 边界 ≤ 0.35 | 只认黑绸会把"压在披帛上的那半边花瓣"整块误杀——**残留的花瓣随后被当成填色源，擦完是一整块褐色**（9:16 S19 实测，最隐蔽的一个坑） |
| G | 金色细线救援：在 mask 邻域内补入 `goldHueAlpha>0.06` 的像素 | 花瓣之间的金色描线亮度常 60~100，过不了 `L>=100`，漏掉会留下"金色鬼影轮廓" |
| H | 深色花体生长：在 mask 邻域内，把"不属于任何干净底色且 `sat>0.30`"的连通块并入，再做**开运算**剪细尾 | 花的暗部/叶影漏掉会留下"花形灰影"；开运算用来剪掉顺着披帛暗边爬出去的细条 |
| I | 掩膜外扩一圈（`D≈0.012·min(w,h)`），守卫：不进开口框、不上披帛本体、不进背景 | 吞掉抗锯齿边与细碎遗漏 |

**③ 填色：源壳 Voronoi + 粗网格中位数底色场（本架构的核心）**

```
源   = mask 外扩 SR≈7~16px 的壳层（跳过内侧 6px 抗锯齿），只采「非红的绸面」
归属 = 多源 BFS，每个待填像素归到最近的壳像素（Voronoi）
底色 = 把壳源投到 CS≈0.022·min(w,h) 的粗网格、每格取【中位数】色，
       空格靠邻格扩散补齐 → 网格平滑 3 遍 → 双线性插值取值
结果 = 底色(x,y) + clamp(源色 - 底色(源), ±hiL)，hiL = min(HI, max(3, 0.15·底色亮度))
```

四个"为什么"：

1. **不用「按开口中线镜像拷贝」**：镜像轴固定在开口中线，只对"紧贴开口两侧"的缺口成立。
   花在开口左上角、离中线大半个开口宽时，镜像点落到开口对侧的深阴影区，采回一条根本不存在的暗带 →
   填出与花同形的纯黑块，盖章后就是一圈黑色描边。
2. **不用全局平面拟合**：一幅绸面里亮带与暗部并存，最小二乘会被一起拉平，在花的位置给出偏亮偏暖的值。
   实测同一格：真值 `(30,29,30)`，平面给 `(47,35,40)` —— 差 50%，贴上去就是一块看得见的补丁。
   中位数对"亮暗混在一起"不敏感，扩散又能跟上局部明暗。**双线性插值**不可省，否则擦除区显出一格一格方块。
3. **残差必须按局部亮度成比例**：固定 ±16 投在 `L≈20` 的黑绸上就是 80% 的起伏，会把擦除区糊成一块斑。
4. **源只取非红绸面**：花往往夹在开口滚边与披帛之间，两侧都是红；一旦把红像素也当源，
   Voronoi 会让整个缺口倒向红域 → 擦完是一整块褐色。反正盖上去的花会覆盖这些位置，填成绸面最安全。

**④ 盖章：精灵等比缩放**

`scale = 目标开口宽 / B1开口宽(338)`，落点 `left = open.x0 - 291*scale`、`top = open.y0 - 380*scale`
（`B1_OPEN = {x0:291,y0:380,x1:629,y1:933}`，即 1000² 胸口裁片里的皮肤块 #117，fill 0.682）。
亮度按「本镜黑绸亮度 / B1 黑绸亮度」整体缩放（钳位 0.55~1.35）。

**⚠ 精灵的 alpha 必须足够陡。** 原来 `alpha=(sat-0.16)/0.14`：奶白花瓣 `sat≈0.24` 只拿到 0.57，
盖章后底层透出来 —— 在红披帛上就变成"红牡丹"。改成 `(sat-0.13)/0.07`（陡坡 + 低门槛）+
「大半径模糊取地板」补针眼后，花瓣一进色相窗口就是实心。

**验证工具**

| 脚本 | 用途 |
|---|---|
| `decal-stamp.js` | 主流程。调试开关：`CMV_LOG_SRC` `CMV_DUMP`(绿=掩膜叠原图) `CMV_DUMP2`(分类图) `CMV_SNAP`(掩膜分阶段快照) `CMV_FILL_DEBUG`(填充物染品红) `CMV_FILL_TRACE`(打印平面/源/结果) `CMV_HI` `CMV_D` |
| `zoomq.js` / `zoomf.js` | 以开口为中心出「原/擦/成/B1」四连瓦片；`CMV_BOX="x,y,side"` 手动窗口，`CMV_OPEN="x0,y0,x1,y1"` 手动归一化开口 |

**排查顺序（照这个顺序找，不要跳）**：`CMV_SNAP` 看掩膜是在哪一步漏的 →
`CMV_FILL_DEBUG` 确认褐色/暗斑到底是被填的还是没擦的 → `CMV_FILL_TRACE` 看源像素与底色场取值。

### 3.11 盖章侧的两道门：可贴区 + 披帛遮挡 —— 2026-10-01（**部分已被 §3.12 取代**）

> ⚠️ 本节的「两道门 + 闭运算 + **基准用擦后图**」在 S18/S19 修复轮中被证伪并整体重写。
> 请直接看 §3.12；本节仅保留其**症状描述**与「掩膜喂 sharp 必须 0/255」「stampSprite 第一参数是路径」两条仍有效的坑位。

**症状**：擦花已经很干净，但盖上去的花**压到红披肩 / 前景物体**上（169-S06/S18、916-S19）。
精灵是硬贴的：只要目标镜的黑绸容不下这朵花，花就会盖到不该盖的东西上。

**根因是"物理层级"**：披帛搭在旗袍**外层**，伞杆在人物**手前**。绣花不可能盖在它们之上。
所以盖章不能无条件贴，必须先算一张「放行度」掩膜，再把精灵 alpha 乘上去。

**两道门（取 min 合成）**

1. **可贴区 `pasteMaskOf`（主门，通用）** —— 绣花只能出现在黑绸上。
   - 判据 = `L < 120 && (r − b) < 25`，再取面积 ≥ 0.4% 画幅的连通块，最后挖掉开口框。
   - **别用饱和度**：黑绸是深蓝调，实测 `(25,30,48)` 的 sat 就有 0.48，和红披帛 0.75 / 皮肤 0.20
     分不干净 → 会把整件旗袍判成不可贴，花被切掉一半（S06 实测）。`r − b` 才分得开：
     黑绸 −20 通过 / 披帛 +112、伞杆 +70、皮肤 +60 全部挡住。
   - 基准用**擦后图**：擦除已把原花位置填成黑绸，所以花位本身可贴；而披帛/杆子/背景擦除前后不变，会被挡掉。
2. **披帛遮挡 `capeMaskOf`（辅门）** —— 高饱和红大块，`sat ≥ 0.45 && (hue < 22 || hue > 342)`。
   - 必须是「红」而不是「暖」：`hue < 32` 会把肤色高光 `(182,137,105) sat=0.42 hue=25` 吃进来。
   - 基准必须用**原图**：擦后图在原花覆盖处已填成黑绸，披帛掩膜凭空缺一块（S06 实测只遮到 2px）。
   - **必须做闭运算**：披帛被原图那朵花盖住的地方是断开的，缺口宽 = 花压到披帛上的深度
     （40~60px）。`blur(sigma) > 128` 等价中值滤波，`sigma ≈ 0.02·min(w,h)` 能把缺口填平。

**三个隐蔽的坑**

- **掩膜喂 sharp 必须是 0/255**。写 0/1 的话 blur 输出恒 ≤1，后续 `> 128` 判据永不成立，
  整张掩膜**静默变全 0** —— 遮挡看起来"跑了"，其实什么都没做（还打印出一个虚高的百分比）。
- **掩膜语义要在调用处对齐**。`gate = min(可贴度, 255 − 披帛度)` 是「放行度」，
  使用处必须写 `alpha × gate / 255`。写成 `alpha × (255 − gate) / 255` 会把语义反过来，
  可贴区被整片裁掉（S06 实测切掉半朵花）。
- **`stampSprite` 的第一参数是路径不是 Buffer**。直接 `buf[i*3]` 全是 NaN，
  而 `NaN < 阈值` 恒为 false → 判据静默失效。要用像素就先 `sharp(p).raw().toBuffer()`。

**调试入口**：`CMV_LOG_CAPE=1`（打印 warm/大块/闭运算/fade 各级像素数）、
`CMV_DUMP_PASTE=region/pm_X`（导出 paste/gate/cape 三张掩膜）、`CMV_SILK_L`、`CMV_SILK_RB`、
`CMV_CAPE_K`、`CMV_CAPE_SOFT`、`CMV_PASTE_SOFT`。
排查顺序：先看掩膜图对不对 → 再看 gate 合成 → 最后看使用处算式方向。

**代价与判断**：遮挡比例 19%~63%（含大量边缘羽化像素，不代表面积损失这么大）。
花被披帛压掉一角在物理上是**正确**的（真实照片里披帛就是会盖住绣花），
比"花盖在披帛上"可接受得多；只有当花被切掉超过一半才需要回头查掩膜。

### 3.12 盖章放行度重写：原图基准 + 几何归属 + 颈部硬边界（v16）—— 2026-10-01

**症状**：S18/S19 按 §3.11 修完，花**仍然**压在红披帛上（用户复报「S18 S19 还有这个问题」）。

**一句话根因**：§3.11 的所有判据都以**擦后图**为基准，而擦除恰恰把「花位」填成了绸面色
——于是**在花位，一切判据都认为那里是干净的绸子**，披帛掩膜在原花覆盖处凭空缺一块，花照贴。
擦后图在花位还有**填充伪影**（`mk18_silk.png`：足迹内整片全黑），会让基于它的绸面判据整片失效。

**结论（血的教训）**：**凡是用来判断「这个像素属于什么」的判据，一律读原图。**
擦后图只能用于「擦得干不干净」的质检，**绝不能**用于归属判断。

**新架构 `pasteGateOf`：一道门，三条判据串行**

```
输入：origRaw（原图 RGBA）、midRaw（擦后图）、open（开口框）、win（窗口）
输出：gate[] —— 0 = 禁贴，255 = 放行（再乘到精灵 alpha 上）

① 原花足迹 fp
   |orig − mid| 的 R+G+B 差和 > 36  → fp=1，再膨胀 3px
   作用：把「这里原来是花」的区域单独圈出来，后面走几何归属而非颜色判据。

② 可见红 bigRed（原图，足迹【外】）
   sat ≥ 0.45 && (hue < 22 || hue > 342)
   只认面积 ≥ MINRED（默认 500）的大块；再剔除「包围盒含开口中心」的滚边环。
   → 命中即 gate=0。
   为什么要面积门限：唇、耳环、花瓣内部碎红点 / 金线反光会零星命中，
   小块全放行，只有成片的披帛 / 披风才该挡花。

③ 足迹内归属 cls（多源 BFS，窗口内）
   种子 = 满足「非足迹 ∧ ( 大红 ∨ 绸面 )」的像素，标 1=披帛 / 2=绸面。
   未知像素按最近已知邻居归属（Voronoi 传播）。
   → 判定：fp ∧ cls==1 → gate=0（花压到披帛 = 物理正确，沿内缘压掉）
          fp ∧ cls==2 → gate=255（花落在绸子上，正常贴）
   注意：绸面判据同样必须用**原图**（midRaw 在足迹内是伪影）。

④ 剩余像素（非红、非足迹）
   L = 0.299r+0.587g+0.114b  （原图）
   gate = (L < SILK_L && r − b < SILK_RB) ? 255 : 0
```

**几何硬边界 `aboveClip`（颈部守卫）—— 关键创新**

- 症状：擦除把**脖子下沿**擦成一块棕灰矩形（`maskGreen` 显示脖子下一块绿）。
- 为什么颜色判据无效：本镜脖子暗部实测 `(140,95,47) sat 0.66 hue 31 L 103`，
  花叶暗金 `(155,111,64) sat 0.59 hue 31 L 119` —— **几乎同色**，任何色相/饱和度阈值都切不开。
- 于是改用**纯几何**：
  ```js
  const clipTop = open.y0 - Math.round(0.25 * open.bw);   // 开口顶线以上 0.25 倍开口宽
  const aboveClip = (i) => ((i - (i % w)) / w) < clipTop;
  ```
  依据：B1 精灵顶点只在开口顶线以上 `30/338 = 0.089` 倍开口宽，取 0.25 留 ~2.8 倍余量；
  脖子在 0.6 倍开外，一定被切掉。
- **应用点必须全**：擦花链的 4 处（候选 / 金色救援 / 深色生长 / 外扩）逐个加 `if (aboveClip(i)) continue;`，
  漏一处就前功尽弃。

**修补算法同步升级（亮暗并存场景）**

全局平面拟合**弃用**：亮暗并存会被拉平。实测邻格真值 `(30,29,30)`，平面给 `(47,35,40)`。
改为：
- **粗网格中位数底色场**（格边长 `CS = 0.022·min(w,h)`）+ **3 次网格平滑**；
- 双线性插值取样 + **最近源传播（Voronoi）** 补空洞；
- **按局部亮度成比例的残差钳位**：`min(HI, max(3, 0.15·Lp))` —— 亮处允许多修，暗处少修。

**羽化默认值**：`CMV_PASTE_SOFT ?? 4`（比旧的 2 更自然）。

**排查工具链（按顺序用，成本从低到高）**

1. `dbg-gateov2.js` —— **本轮最有用**。统计精灵实心像素的 gate 分布，并打印 46×46 ASCII gate 图
   （`#` = 0 禁贴 / `.` = 255 放行）。一眼看出「花被哪条判据切了、切在哪」。
2. `CMV_DUMP_MASKS=region/mk` —— 导出 `fp / red / cls / silk` 四层掩膜，逐层核对。

4. `dbg-gateov.js` —— gate 叠原图（红=禁贴，青=精灵轮廓）。
5. 调参入口：`CMV_MINRED`、`CMV_SILK_L`、`CMV_SILK_RB`、`CMV_PASTE_SOFT`、
   `CMV_NO_GOLD`、`CMV_NO_DARK`（隔离变量法：关掉一条链路看症状是否消失，快速定位贡献者）。

### 3.13 擦除的六处补丁：三带活动区 / 细长高光 / 滚边 / 奶白花瓣 / 冷暖 / 灰雾（v17）—— 2026-10-01

**背景**：§3.12 修完 S18/S19 花压披帛，用户过闸时提要求「尽量优化到 B1 的程度」。
全量跑 169 后才暴露：§3.12 的花盒**自身**引入了两个新缺陷，另有三处老缺陷浮出水面。

#### ① 花的活动区必须拆成「三带」，不能用一个外接框

§3.12 用 B1 精灵外接框当花盒，两头不讨好：
- **收紧** → 169-S22 的左花最左伸到开口左缘外 **1.0·bw**，被盒边界切掉半边，
  擦完留下整朵花影；盖章后**原影与新花重影**，比不擦更难看。
- **放宽** → 169-S18 的**木盒上边缘高光**在开口正下方 **0.89·bw**、
  **大腿红饰**在正下方 **4.2·bw**，都会被当花擦掉，填出一块纯黑补丁（黑洞）。

**关键洞察**：两者的「离开口距离」是同一量级，用距离分不开；但**方位**分得开 ——
花只长在开口的**左右两侧**，从不长在**正下方**。

```js
const bandX = 0.90 * open.bw;   // 左右带宽度
const bandU = 1.30 * open.bw;   // 上方带高度（B1 花顶 = 开口顶外 1.124·bw）
const bandD = 0.12 * open.bw;   // 下方只留一线余量
const inFlowerBox = (i) => {
  const x = i % w, y = (i - x) / w;
  if (y > open.y1 + bandD || y < open.y0 - bandU) return false;  // 开口正下方远处出局
  if (x >= open.x0 && x <= open.x1) return true;                 // 开口本体
  // 两侧带的 y 范围必须与开口同高 —— B1 左花 y∈[0,922]、开口 y∈[380,933]，
  // 花有一多半长在开口顶线【以上】；若限制 y ≥ open.y0 会把花上半切掉
  // （916-S11 实测：候选直接归零，报「未找到刺绣」）
  return (x >= open.x0 - bandX && x < open.x0) || (x > open.x1 && x <= open.x1 + bandX);
};
```

#### ② 细长高光条 = 误检（紧凑度门槛）

木盒上边缘的高光是一条又细又长的亮带，`L≥100 + 邻接黑绸` 全部通过，
再由 ③c 深色生长蔓延成**整只木盒 + 手**（169-S18 实测黑洞）。
真花是**实心云状**（bbox 填充率实测 0.3~0.6），细亮条 < 0.1 —— 一刀分开：

```js
if (c.area / Math.max(1, c.bw * c.bh) < 0.18) continue;   // 细长条 = 高光边，不是花
```

#### ③ 红滚边是「细长线状红」，不是「小块红花叶」

滚边环面积（周长×线宽 ≈ 7.5k px）刚好卡在 `n·0.0025`（9.7k）之下，
旧逻辑把它归进 `redSmall`，于是 ③c 当花叶吃掉 → 擦完水滴口左缘滚边**断掉一小截**。
按填充率再分一层：

```js
if (c.area >= n * 0.0025) bigId[c.id] = 1;         // 披帛 / 盘扣
else if (fill < 0.20)     smlId[c.id] = 2;         // 2 = 线状红（滚边 / 描边）
else                      smlId[c.id] = 1;         // 1 = 花叶
// 使用处 `if (redM[i] && !redSmall[i]) continue;` → 线状红自动被保护
```

#### ④ 深色生长里的 `isSkin` 只该管「开口顶线以上」

`isSkin`（hue 4~48）会把**奶白花瓣的暗部**整片排除，花瓣留在原地 →
填色源壳采到它 → 擦完是一块**偏亮的灰雾**（169-S22 的白色牡丹最典型）。
开口内的皮肤另有 `ex` 矩形排除，不需要这条兜底：

```js
{ const yy = (i - (i % w)) / w; if (yy < open.y0 && isSkin(r, g, b)) continue; }
```

#### ⑤ 低饱和像素必须分冷暖

`if (s <= 0.30) continue;` 一刀切会把奶白 / 香槟花瓣（sat 0.10~0.20）全挡在门外。
**绸面亮带是冷色蓝灰**（`(58,67,81)`，r−b ≈ −20），**花瓣是暖色**（`(196,151,93)`，r−b ≈ +100）：

```js
if (s <= 0.30 && (r - b) < 30) continue;
```

#### ⑥ 填色的源壳必须是「干净黑绸」

源壳环（距 mask 6~SR px）常压在花的残影、花瓣抗锯齿边、绸面高光带上。
采到亮像素 → Voronoi 把整片缺口拉亮 → **灰雾**。加一道：

```js
if (Lof(i) >= 95 || satOf(i) >= 0.42) continue;
```

#### ⑦ 顺带修正：「无花镜头」必须能正确跳过

169-S03/S30、916-S14/S18/S23/S29 的原图旗袍上**本来就没有刺绣**（干净黑旗袍，已逐镜裁图确认）。
旧版会给它们擦出 ~1% 的误擦（背景霓虹、绸面高光）。现在候选全被过滤 → `未找到刺绣` → 跳过擦除，
**但仍照常盖章贴花**（角色设定要求旗袍始终有花，这是对的）。

**全量结果（2026-10-01）**

| 版本 | 总镜 | 实际擦除 | 跳过 |
|---|---|---|---|
| 169 | 36 | 28 | 8（6 空镜 + 2 无花） |
| 916 | 38 | 22 | 16（8 空镜 + 8 无花） |

擦除量 0.05%~1.06%（旧版 0.77%~3.33%，差值主要是旧版的误擦）。

### 3.14 角色参考图集：审计 → 重建 → Reference-First 生成（v7）—— 2026-10-01

**起因**：用户看过成品总览后指出「花还是差别，左右不对称，有的腰间、有的腹部、有的没有，有的衣服不对」。

#### 一、先审计参考图集本身，别急着改生成

三条实测（审计脚本一眼出图）：

1. **参考图集自相矛盾**：`ref_face`(=B1) 是「宽水滴 ≈2/3 胸宽 + 无蕾丝袖 + 开口上缘左右各一朵花」，

   → **五张参考图五个样**，用它做参考也锁不住。
2. **流水线根本没挂全身参考图**：`regen-clean.js` 自述 "T2I-first, swap-last" ——
   普通镜 Step A 纯文字 T2I（`images` 为空）、Step B 只换脸；五张 `ref_body_*.png` **从未进入生成**。
3. **成品底图跨镜完全不一致**：169 S06 无花 / S18 只有左花且很高 / S22 两侧大花靠外 / S31 只有右花；
   916 S19/S25/S31 全部只有右侧一朵（即"左右不对称"）。

#### 二、B1 权威规格必须**放大目检**，不能凭缩略图

放大 B1 肩部后才发现与旧 prompt 的三处冲突：

|---|---|---|
| 袖 | `short sheer black lace cap sleeves` | **无蕾丝袖**（披帛直覆肩头，露裸臂）|

**零额度权威细节**：从 B1 直接硬裁 `ref_chest_b1` / `ref_shoulder_b1` / `ref_collar_b1` / `ref_acc_b1`
（与 B1 **100% 同源**，比任何"重新生成一张细节图"都可靠）。

#### 三、派生全身多视角：**prompt 顺序的权重 ≥ 内容本身**（本轮最大教训）

用 `B1 + ref_chest_b1` 双图 i2i 派生五视角，两版对比：

- **v1（`ANGLES` 紧随 "Picture N = ..." 说明）** → 全身 / 角度 / 背面**全部正确**
- **v2（把长段胸/花 `SPEC_HEAD` 插在 `ANGLES` 之前）** → 构图指令被挤出关键位，
  模型转而**强模仿 Picture 1（半身正面）**：五张全变半身、角度全丢、**蕾丝袖回归**

> **铁律：多图 i2i 时，最硬的约束（构图 / 角度 / 全身还是半身）必须放在最前位，
> 紧跟 "Picture N = ..." 的说明之后。内容写对但位置靠后 = 无效。**
> 同理「NO lace sleeves」在 v1 的 SPEC 中部有效、在 v2 的 `SPEC_BODY`（末尾）失效。
> 修法：`prompt = Picture说明 + ANGLES + SPEC_HEAD + SPEC_BODY + STYLE`。

#### 四、Reference-First 生成（v7）

```
Step A  images = [ref_body_<angle>, ref_face, ref_chest_b1]
        prompt = HEAD_LOCK + core(场景) + IDENT + WARDROBE + REF_NOTE + STYLE + LOCKS
        REF_NOTE 明写：P1 只取身份与服装、P2 只取脸、P3 只取胸口细节；
                      并**显式禁止照搬参考图的棚拍姿态 / 灰底 / 全身构图**
```

`front` → `ref_body_front`；`three-quarter-left` → `ref_body_3q-left`；

`side-right` → `ref_body_side-right`（= side 的**水平镜像**，`sharp.flop()` 零额度）；
`back` → `ref_body_back`。

#### 五、两条附带的实测结论

1. **`characters_view` 在 T2I-first 下完全失效**：169-S18 / S22 要求 `back`，却生成正面胸口。

   参考图只负责身份、服装、水滴口、身材。**两条线分工，不互相替代。**

**试点证据（169 S06 / S18 / S16）**：v7 的 S06 与 B1 在**水滴口宽度 + 开口上缘双花位置**上几乎逐点对齐，

**新增诊断工具**：`cut.js`（任意区域裁剪并排）、`make-thumbs.js`（批量缩略图）、
`dbg-open.js`（对比 skin / ring 两种开口检测）、`dbg-flower.js`（量掩膜各连通块 bbox 与填充率）、

### 3.15 「绝对孤立」：场景文案本身就是额外人物的来源 —— 2026-10-01

**症状**：`LOCKS` 里明明写着 `EXACTLY ONE WOMAN — she is completely alone`，画面里仍然冒出额外的人
（169-S16 背景生成出**两名摊贩**；早期 169-S09 出过双人）。

**根因**：额外的人不是模型幻觉，而是**被场景文案点名要求画出来的**。
storyboard 的 `keyframe_prompt` 逐镜自带场景描述，其中常含人类名词：

| 镜 | 场景原文 | 后果 |
|---|---|---|
| 169-S16 | `The **vendor's** warm orange stove glow catches her face` | 生成摊贩 |
| 169-S02 | `Blurred **silhouettes of well-dressed guests** in the background` | 生成背景宾客 |
| 169-S07 | `silhouettes of well-dressed **revellers** walk into the warm amber light` | 生成路人 |
| 169-S23 | `in front of a blurred **guest** inside a lantern-lit pavilion` | 生成宾客 |

**为什么末尾的抽象否定压不住**：`EXACTLY ONE WOMAN` 是**抽象否定**，而 `The vendor's stove glow` 是**具体名词**。
具体名词的权重高于抽象否定 —— 模型会忠实地把 vendor 画出来。叠加 §3.14 的**顺序**教训
（写在 prompt 末尾的约束权重趋近于 0），双重失效。

**修法（三步，缺一不可）**：

1. **场景级清洗表 `SCRUB`**（按 `ratio→镜号` 索引）：把场景句里的「人」**就地改写成「物 / 空景」**，
   保留光、天气、水面、建筑，只去掉人。
   - `The vendor's warm orange stove glow` → `The glow of an unattended warm orange stove`（+ `the stall stands empty with no vendor present`）
   - `silhouettes of well-dressed guests in the background` → `The background is completely empty — only warm amber light and soft out-of-focus bokeh`
   - `silhouettes of well-dressed revellers walk into the warm amber light` → `the street is utterly deserted — only warm amber light and drifting rain`
   - `in front of a blurred guest inside a lantern-lit pavilion` → `inside an utterly empty lantern-lit pavilion`
   - **逐条替换必须打印命中日志**，`未命中` 要报警（字符串不匹配会**静默不改**，等于没修）。
2. **孤立硬锁 `ISOLATION` 紧跟场景文案之后**（不是末尾）：
   `HEAD_LOCK + core + ISOLATION + IDENT + WARDROBE + ... + LOCKS`。
   锁内显式**点名**可能出现的角色并禁止：`if the scene text mentions a vendor / guests / revellers /
   passers-by / a crowd / figures / silhouettes ... DO NOT draw any of them`，
   并要求"把该处渲染为**空无一人的**环境，只留光、物、天气、水面、建筑"。
   同时封堵全部伪装通道：`not even blurred, out-of-focus, distant, mirrored, partial or implied`。
3. **空镜也要加 `NO_PEOPLE`**：空镜走 `core + NO_PEOPLE + STYLE`，否则纯文字路径完全没有孤立约束。

**审计纪律：命中 ≠ 一定有额外人，必须逐条人眼复核。** `dbg-people.js` 扫出 169 有 12 镜命中人类名词，
但逐句看上下文后：

| 类型 | 镜 | 处置 |
|---|---|---|
| 真路人 | S02 / S07 / S16 / S23 | **清洗** |
| **主角本人的倒影** | S10（`reflected across the wet glass ... silhouette of a young woman`） | 保留 —— 是她自己的镜像，不违反孤立 |
| **主角本人** | S35（`One single tiny figure of a woman walks`） | 保留 |
| **正则误报** | S28（`silhouettes of ... grey clay-tile **rooflines**`） | 无需处理 —— 是屋檐剪影不是人 |

反之，**文案没命中也不等于安全**（模型仍可能自行加人），所以清洗之外还需**全量成品人眼巡检**。

**新增诊断工具**：`dbg-people.js <169|916>` —— 扫 storyboard 全部文案字段（`keyframe_prompt` /
`visual` / `subject_action` / `action`）中的 60 余个人类名词，列出命中镜与命中字段，并支持句型去重以区分「泛指主角」与「真路人」。

**一句话**：孤立约束不能只写在 prompt 里，**必须先把场景文案里的人拿掉**；锁要贴在场景文案后面，而不是末尾。

#### 进阶：清洗之后仍然出双人 —— 两个更深的根因（同日实测）

清掉场景里的路人后，169 仍有 4 镜（S02/S16/S23/S30）顽固地画出两个人。逐项对照后定位到两个**与"否定词"无关**的根因：

**根因 A：prompt 里出现了两个"不定指的女人"。**

- 场景文案写 `A young female singer glides...` / `Close-up of a young female singer's face`
- 身份块写 `A young East Asian woman in her early twenties...`

两个互不相干的**不定冠词短语** → 模型当成两个人画。修法：
1. 身份块改成**回指**：`SHE — the one and only person in this frame — is ...`；
2. 孤立锁里显式声明 **"场景里的歌手 = 下方描述的女人，是同一人"**（`ONE AND THE SAME single person — do NOT treat them as two people`）。

**根因 B：一次给多张参考图，模型会当成"多个主体"。**

三档对照实测（同一镜 S30、同一 prompt，只改参考图张数）：

| 参考图张数 | 结果 |
|---|---|
| 3 张（全身 + 脸特写 + 胸口） | **两张脸**（双人） |
| 2 张（全身 + 脸） | 单人 ✓ 但场景崩成沙漠 |
| 1 张（仅脸） | 单人 ✓ 但场景崩成沙漠 |

降图数能去双人，却**丢掉锚定、场景保真崩坏**，不可取。正解是
**合板（sheet）**：把三张预先 `sharp` 拼成**一张**设定图，只传一张 ——
信息全保留，又不给模型"多个主体"的暗示。实测 S02 / S23 **双人消失且场景保住**；
对照组 S03 / S06（原本合格）用合板后依然正常，说明合板不会破坏好镜。

合板的两个必要条件：
- 必须在 `SHEET_NOTE` 里写明 **"这是一张设定图，不是要照抄的构图"**，
  否则模型会把三格并排的版式直接画进成片；
- 合板底色用中性灰，并与"不要复制灰底"的指令配套。

**合板也不能包治百病**：S16（街边小吃摊）折叠后仍会画出摊贩，
最有效的仍是**改场景本身**——`street-food cart` → `old, DESERTED street-food cart`，
并补 `the whole street is completely empty behind her`；
S30（特写）用合板后丢掉了特写构图，需要把场景句强化成
`EXTREME CLOSE-UP that fills the entire frame ... against a completely empty dark background`。

**残留策略**：这类失败带**随机性**（同 prompt 同参数，S11/S15 单脸成功而 S30 双脸），
所以最终应走 **best-of-N + 目检择一**，而不是指望单次一定通过。

#### 三条反直觉的补丁（都是实测踩出来的）

1. **孤立锁里绝对不要枚举人类名词。** 早期版本写
   `if the scene mentions a vendor / guests / revellers / passers-by / a crowd ... DO NOT draw them`，
   甚至写 `no vendor, no cook, no customer` —— **两个候选都画出了摊贩**。
   把词喂给模型等于反向诱导。**改成只描述"空"，不点名"人"**：
   `Anything the scene text implies that would place other human beings in the shot must be omitted
   entirely: render those parts as an empty, deserted environment showing only light, objects,
   weather, water and architecture.`
2. **场景物体本身会召唤它的从业者。** 169-S16 写 `street-food cart` / `night-market stall` 都出摊贩
   （改成 `market` 更糟 —— 直接生成一条人挤人的夜市）。**最终解法是把该物体移出画框**：
   `standing before an old street-food cart` → `standing alone in an utterly empty rain-soaked street`，
   光源改为 `a warm orange stove glow from just off-frame`。
   **画框里没有可站人的摊位，就没有摊贩。**
3. **前景的"手"是第三人的肢体。** 169-S24 写 `a blurred hand in a silk sleeve lifting a cup`
   → 生成一条**画外的裸手臂**（且她右手凭空多出一只杯子）。改写成 `that hand is HERS` 无效，
   直接**把前景的手从场景里删掉**才干净。

#### 合板的代价（必须知道）

合板模式能消灭双人，但模型会偏向**中性影棚半身像**，丢掉戏剧性构图
（S24 的"瞳孔里的灯笼倒影"、S30 的"脸部大特写"都退化成了普通胸像）。
可用 `SCENE_FIRST` 把场景句提到最前缓解（S30 因此恢复了"眼睛缓缓闭上"的动作节拍），
但**不保证完全恢复**。因此合板只对**失败的镜**按需启用，不要在好镜上全量替换。

**最终裁决标准**：不是"prompt 里有没有写孤立"，而是**逐镜放大、人眼数人头**（§3.14 的"先量再看"）。

### 3.16 参考图集自身的 canon 缺陷会被整条流水线放大 —— 2026-10-02

**症状**：Reference-First 架构下（§3.14）已把参考图挂进关键帧生成，一致性明显变好，
但**背面镜头背上仍开花、后背还开了水滴口**，侧面参考图**裙摆多一朵花且被裁成半身**。

**一句话根因**：问题不在关键帧 prompt，而在**参考图集本身**。
一张有缺陷的参考图会被它覆盖的所有镜头持续污染——`ref_body_back.png` 有缺陷直接波及
**169 的 9 镜 + 916 的 6 镜 = 15 镜**。所以**换新参考图后必须对整套六视角逐一过 canon 自检**，
不能只管"这次要用的那张"。

#### 三条可复用的规则

1. **视角生成时，第二张参考图必须是"全身图"，不能是"局部特写"。**
   `derive-refs.js` 给每个视角都喂了 `ref_chest_b1.png`（胸口水滴口 + 双花的**近景裁切**）。
   实测两个泄漏：
   - 把**水滴口 + 双花**直接搬到**后背**（back 视角）；
   - 把**近景构图**带到侧视图 → side 被裁成半身。
   改成锚点图 `[B1, ref_body_front.png（全身正面）]` 后，背面立刻回正、侧面立刻恢复全身。
   → 规则：**局部特写参考图只用于它本来那个部位**；派生其他视角时用全身图当锚点。

2. **"加形容词"治不了构图级缺陷，"构图级 CRITICAL"才能。**
   side 参考图裙摆多花，写 `NO flower on the hip, waist or skirt` 仍然复发
   —— 因为**近景裁切的构图暗示强于文字否定**。有效写法是加**构图级硬约束**：
   `CRITICAL — FULL-LENGTH FRAMING, HEAD TO TOE ... do NOT crop at the waist, the hip, the thigh or the knee.`
   同理 back 视角要写 `CRITICAL — THE BACK OF THE DRESS IS TOTALLY CLOSED: the keyhole exists on the FRONT only`
   （明写"只在正面"比只写"背面不要有"更有效）。

3. **左右两张侧视图用镜像保证对称。**
   用户抱怨的"左右不对称"可以从构造上消灭：`side-right` = `side` 用 sharp `.flop()`
   水平翻转得到（不是重新生成）。代价是侧缝开衩会跟到另一侧，属可接受
   （原图两侧都画了开衩）。**重新生成两张"侧面"必然产生两套细节**，镜像则天然一致。

#### 配套工具（本轮新增）

| 脚本 | 作用 |
|---|---|
| `fix-refs-v4.js` | 定向重出某视角参考图；两图锚定 = `[B1, 全身正面]`；含构图级 CRITICAL |
| `mirror-refs.js` | 把一套 canon 参考图镜像到另一画幅目录 + **md5 校验** + storyboard 视角覆盖校验 |
| `refcmp.js` | before/after 拼图（带标签），供人眼目检 |

> **Windows 坑**：node 里 `execSync("md5sum ...")` 会走 cmd.exe → 静默返回 "(缺失)"，
> 校验全报失败。**md5 一律用 `crypto.createHash("md5")`**，不要 shell 出去。

#### canon 自检必须「分区放大」，缩略图会骗人

本轮真实踩坑：`ref_body_3q-right.png` 的**胯部有一朵大金牡丹**，
在 6 格缩略拼图里**完全看不见**（因为拼图把 9:16 压到 900px 高，花只占几十像素），
肉眼过两遍都漏掉，直到把下半部裁出来放大才发现。

→ **canon 自检标准动作**：对每张参考图**按区裁切放大**至少三块 ——
① 胸口/领口（花位是否只在开口上缘）；② **腰以下至裙摆（是否有花/开衩异常）**；③ 肩臂（是否有袖）。
`_qa/region/_lower/*.png` + `refs_v4_lowerbody.jpg` 就是这张「下半身审计图」的做法：
`sharp.extract({top: 0.45*H, height: 0.55*H})` 六视角并排。
**"花只在胸口开口上缘、其它部位纯黑"是 canon 里最容易破的一条**，而它几乎全部破在下半身。

**流程补丁**：修 canon 参考图 → **原图先 `cp` 进 `_archive/refs_pre_<原因>_<日期>/`** → 再覆盖 →
出 before/after 拼图 + **分区放大审计图**交用户目检 → 通过后 `mirror-refs.js --apply` 同步到另一画幅目录。
**参考图一改，该画幅已生成的关键帧即全部作废**（V7 产物基于旧参考），必须记录重跑清单。

### 3.17 Reference-First 的三个真实失效点 —— 2026-10-02 实测

**背景**：参考图集修干净后（§3.16）按清单重跑 169 的 16 镜，目检发现 **10/16 不合格**。
三次定向试点定位到三个**互相独立**的失效点，都不是个案。

#### 失效点 1：视角只活在「选图」里，不活在「文字」里

**症状**：`characters_view = back` 的 **8/8 镜全部被画成正脸**（S05/S09/S12/S18/S22/S25/S29/S35）。

**根因**：`characters_view` 以前**只用来挑参考图**，从来没写进 prompt。而参考图是**三张**：
角度全身图 + B1 正脸肖像 + 胸口特写。后两张都是正脸 —— **正脸票 2:1，压过背面图**。

**修法（两条并用，缺一不可）**：
1. `VIEW_TEXT[characters_view]` 把视角写成文字硬约束，插在 `ISOLATION` 之后、`IDENT` 之前；
2. **back / side 镜不喂正脸参考图** —— 只喂一张角度图，配 `ONE_REF_NOTE`
   （不再声明 "Picture 2 is her face in close-up"）。
   实测：两镜（S12/S22）从"正脸"变为**真正的背影**，且场景没有因此崩塌
   —— §3.14 里"少喂图 → 场景崩"的老结论在 prompt 结构改进后**已不成立**。

#### 失效点 2：正面口吻的服装描述会压过视角锁

**症状**：加了视角锁之后，back 镜**仍然**画成正脸。

**根因**：`WARDROBE` 整段都在描述**正面** —— "a WIDE open water-drop keyhole cutout occupies
the centre of her chest … with her very full bust swelling inside the open teardrop"。
文字里出现了两次「胸口水滴口 + 双乳」，对正面的拉力**强于**一句视角锁。

**修法**：**按视角切服装块** —— `WARDROBE_BACK` / `WARDROBE_SIDE`，把"正面"从文字里
彻底拿掉（背面块只讲"一整片不间断纯黑、无口无花"；侧面块只讲"开口被edge-on看到、
只有靠镜头那一朵花"）。背面另配一个不含胸口描述的 `headLock`。
→ 规则：**视角专属视角块 + 视角专属服装块，必须成对出现。**

#### 失效点 3：多参考图 → 多主体；不定指人名 → 双人

**症状**：双人 / 镜中第二张脸（S02/S09/S10/S14/S33）。

**两个独立成因**：
1. **3 张参考图 = 3 个主体**（§3.15 已记录，但当时只在失败镜上合板，没做成默认）。
   实测：`CMV_REFN=1` 后 S02 的双人**消失**。
2. **文案里的不定指女人**：场景写 `a young female singer`，身份块写 `a young East Asian woman`
   —— 两个**不定指**，模型各画一个。169 有 **28/36 镜**带这个模式（916 是 0）。
   修法：全局 `SUBJECT_SCRUB` 就地改写成回指 ——
   `of a young female singer` → `of HER`、`a young female singer` → `SHE`
   （句法仍自然：`of HER sitting on …`）。实测 S09/S14 双人 → 单人。

#### 按视角的参考图/文案配置表（本轮定型）

| characters_view | 参考图 | 服装块 | 视角块 | isolation |
|---|---|---|---|---|
| front / three-quarter-* | 1–3 张（推荐 1 张） | `WARDROBE` | `VIEW_TEXT` | `ISOLATION` |
| **side-left / side-right** | **1 张（角度图）** | `WARDROBE_SIDE` | 同左 | 同上 |
| **back** | **1 张（角度图）** | `WARDROBE_BACK` | 同左 | 同上 |
| 无人物细节镜 | **0 张（纯文字）** | — | — | `PART_NOTE` |
| 空镜 | 0 张 | — | — | `NO_PEOPLE` |

> **无人物细节镜必须进 `part` 名单**：169-S05 是「齐膝高度只看裙摆下摆」的细节镜，
> 漏在名单外 → 吃到全身参考图后画出一个**完整正脸女人**。
> 判据：文案含 `of the hem` / `at knee height` / `of her hands` / `no people` 等。

| 工具 | 作用 |

### §3.18 「细节镜」若带 characters_view，参考图会劫持构图（169-S17 实测）

**症状**：storyboard 写 *"Close-up of a young woman's slender hands, rubbing together"*，`characters_view` 却标了 `side-left` →
流水线照常喂 `ref_body_side-left.png`（一张全身棚拍图）→ 模型**忽略文字、照抄参考图**，渲染成
「蓝色影棚背景的全身侧身像」，场景全丢。

**根因**：视角锁 + 参考图是为「有脸的全身镜」设计的；细节镜（手 / 下摆 / 脖颈 / 鞋）根本没有脸和全身，
喂全身参考图 = 给模型一个必须复现的强构图，文字被压过。

**修法（三条）**
1. 细节镜一律走**纯文字路径**（等同 `PART`/`EMPTY`），不喂任何人物参考图。
2. 上流水线前必做一次扫描：`close-up of ... (hands|hem|neck|chin|heels|shoes|fingers|wrist)` 且带 `characters_view` 的镜 = 疑似误标，人工确认。
3. 若细节镜确实需要人物一致性（如需要同一双手），**只喂对应局部参考图**，不喂全身图。

> 169 同批还有 S05（`back` + 下摆特写）、S11（`three-quarter-left` + 湿脸特写 → 渲染成室内书房场景）属同一类。

### §3.19 canon 参考图集**自相矛盾**会让「衣服」随机（B1 实测）

**症状**：同一批关键帧里，袖型一会儿「裸肩」一会儿「黑色蕾丝短袖」，用户反馈"有的衣服不对"。

**根因**：B1 canon 的两张图**互相矛盾**——
- `ref_body_front.png`（全身正面）：肩臂由红披风遮住，**读作裸臂**
- `canon/ref_chest_b1.png`（胸口特写）：上臂清楚可见**黑色蕾丝短袖**

多图 i2i 时，模型在两图之间摇摆 → 袖型随机；而文字锁写的是「no lace sleeves, no cap sleeves, bare shoulders」，
只跟全身图一致 → 进一步放大矛盾。

**修法**
1. **canon 必须单源**：细节图只能从全身图裁切而来，**不得独立生成**（否则必然引入新特征）。
2. 上流水线前做一次 canon 自检：把 6 张全身图 + 4 张细节图并排，**逐项对照**（袖型 / 水滴口 / 花位 / 披风 / 鞋）。
   只要有一项对不上，先统一 canon，再生成关键帧。
3. 同类风险项：**披风是否每镜必戴**。若 storyboard 未统一，成片会出现「有的戴、有的没戴」。

### §3.20 花位判定必须在「分区放大」里做，且要区分镜别

- 缩略图**看不见**胯部/裙摆的小花（实测漏检 3q-right 胯部一朵）。
- 但**特写 / 中近景镜的裙摆本来就不在画框内** → 这类镜不存在"裙摆多花"风险，不必审。
- 只有**全景 / 中全景**（腿与下摆入画）才需要跑「下半身分区放大」。
- 标准动作：`zoom-sheet.js`（`CMV_ZONE=torso` 判袖型与胸口花；`CMV_ZONE=lower` 判胸口以外的多花）。

### §3.20b canon 裁决的落地三件套（2026-10-02，B1 实测）

用户对三处 canon 冲突拍板后（**Q1 袖型以 `ref_chest_b1.png` 为准 / Q2 披风非每镜必戴 / Q3 下摆纯黑**），
把它落成代码需要动三个地方 —— 只改参考图或只改文字都不够。

**① 文字必须与参考图**同源**（Q1 —— 这是「衣服不一致」的第一根因）**

- 症状：同为手部特写，916-S07 长出了**长袖**、916-S20 是**全裸臂**、916-S26 领口变**白滚边**。
- 根因：`regen-v7.js` **7 处** prompt 写着 `NO lace sleeves / shoulders completely BARE`，
  而 canon 图 `ref_chest_b1.png` 画的是**黑色蕾丝短袖**。模型在图与文之间**随机二选一** → 跨镜漂移。
- 修法：把 7 处「裸肩」全部改为 `short black scalloped-lace cap sleeves ... the arm below it bare`。
  **参考图一改，全文所有描述它的句子都要跟着改** —— 漏一处就留一个随机源。

**② 细节镜必须带服装块（第二根因）**

- 症状：`part`（局部镜）名单里的镜，衣服完全随机。
- 根因：这条路径的 prompt 只有 `PART_NOTE + ISOLATION`，**一句服装描述都没有**。
- 修法：新增 `WARDROBE_DETAIL` —— **只描述材质与边缘**（领口红滚边 / 黑蕾丝短袖 / 纯黑绸面 / 无花），
  **不描述姿态与构图**（否则会把「手部特写」拽成完整人形）。`isPart` 与自动检测的 `isDetail` 两条路都挂上。
- 配套负例：`EVERY piping edge is deep crimson RED — never white, never ivory, never pale grey.`

**③ 数量类要求必须写负例（Q1 的花 / Q3 的下摆）**

- 「花成对」：`ONE single pair ... one on each side` **压不住** —— 模型把「一朵」也解释成这一对（169-S10/S33、
  916-S04/S05/S23 实测，用户报「一边有花一边没有」）。
  必须升级为 `EXACTLY TWO ... NEVER render only one, and never three or more`。
- 「下摆纯黑」：故事板原文自带 `traced with gold-thread peony embroidery`（169-S05），与 canon 直接冲突 →
  **改文案（SCRUB 表），不是加否定词**。凡是「文案自己要求的」违反 canon 内容，都要在进 prompt 前改掉。

**④ 脸部特写只喂 `ref_face.png`**

face CU 镜喂**全身**参考图 → 模型照抄参考图的全身构图，把「湿发特写」画成完整人像（169-S11 实测）。

**验收要点**：跨镜抽 3 张露臂 / 露领的镜并排放大，袖型与滚边色必须**完全一致**；
花位抽 3 张数花，必须**左右各一朵**。

### §3.20c 无人物镜若带 `characters_view`，等于流水线和故事板自己打架（169-S13 实测）

- 故事板里 S13 的 `video_prompt` 明写 **`EMPTY FRAME LOCK: this shot contains NO human being at all`**，
  `visual` 也写「没有别的，只有她的影子」——**但 `characters_view` 还是 `back`**，
  且它落在 `part` 名单里 → 走了「局部镜 + 服装块」路径 → 成片是一张**躯干像**，影子只退到背景。
- **判据**：`characters_in_shot` 非空 ≠ 画面上有人。**只要 `visual` / `video_prompt` 写的是
  「只有影子 / 只有物件 / 只看到某部位的投影」，`characters_view` 就必须清空**，否则：
  ① 被选进参考图路径；② 被服装块喂出一具身体。
- **修法**：这类镜归入 `empty` 名单（`core + NO_PEOPLE + STYLE`，不喂参考图、不带服装块），
  并把 keyframe 文案里的「一个女人」改写成「一段被拉长的身影轮廓」（去掉不定指女人）。

### §3.21 场景里「有人」的物件会把背景路人召唤回来（169-S24 实测）

- S24 原文是「跟焦镜头：**前景是客人丝绸衣袖的手**端起酒盏，焦点拉到后方的沈棠半张脸」。
  为满足「绝对孤立」把前景的手删掉后，模型**仍然**在背景画出一个端盘子的侍者。
- **根因**：内景（SC1 灯下茶楼）本身就会召唤从业者（同 §3.14 的「夜市摊」教训）。
  删掉文案里的路人名词只能解决一半，**必须把场景改写成「空无一人」**：
  `a completely empty, deserted lantern-lit room with no other person anywhere in the frame`。
- 强化顺序：**改写场景（去人） > 加否定词（不枚举人类名词） > 加孤立锁**。
- **补充（169-S02，2026-10-02 V9 全量实测）**：删掉「背景宾客剪影」那一句**仍然双人**（端茶对坐）。
  真因在剩下的 `carrying a small tray with a porcelain wine cup` —— **端托盘送酒这个「服务性道具＋动作」
  本身就蕴含一个「被服务的人」**，模型必然把那个人补出来。
  → **动作类线索比名词类线索顽固得多**：删名词不够，**得把动作/道具一起删掉**
  （改为只保留姿态本身：`her head turned back over her shoulder in a smile`），再配 `CMV_REFN=1` 降参考图数，实测一次转单人。
  通用规律：**凡「A 为 B 做某事」的文案，即使 B 没被写出来，也一定会被画出来**。

### §3.22 批次验收的「三件套」与两类拼图（流程固化）

固定交付（缺一不可）：① **验收单拼图**（状态色 + 镜号 + 一句结论 + PASS/FAIL/待定 计数 + 图例）；
② **逐镜核对表**（`镜号 | 要求 | 判定 | 失败原因`）；③ **一句待决问题 + 选项与后果**。

| 拼图 | 脚本 | 用途 |
|---|---|---|
| 分组巡检 | `audit-sheet.js <169\|916>` | 按 `characters_view` 自动分组，一屏看一组 |
| 验收单 | `build-gates.js`（判分表写死在脚本里） | 带 🟩/🟥/🟨 状态色的终审单 |
| 躯干/下半身放大 | `zoom-sheet.js <r> <out> <ids>`，`CMV_ZONE=torso\|lower` | **缩略图看不见的花位必须靠它** |
| 修前/修后 | `build-ba2.js <r> <S10,S33,...>` | 红=修前 / 绿=修后，逐对呈报修法有效 |

  **不要再往工具里写死 `_V7`**（本轮踩过：跑批产物是 `_V8`，而工具全在找 `_V7`，静默报「缺产物」）。

### §3.23 袖型「材质」在批次内不统一 → 已验修法（2026-10-02 用户裁决）

- canon `ref_chest_b1.png` 的袖是 **黑色蕾丝网眼短袖**（scalloped lace cap sleeve）；
  但同一批里约一半镜渲染成**光滑黑短袖**（169-S20/S24、916-S04/S19/S36 等）。
- 用户裁决：**袖口统一使用「黑色蕾丝网眼短袖」**。
- **已验证的修法**（V9 试点 5 镜通过）：把袖型从「形容词」升级为「**结构 + 材质 + 边缘 + 负例**」四件套：

  > `short black scalloped-lace MESH cap sleeves: an OPEN-WORK black lace net full of tiny eyelets,`
  > `so the pale skin of her upper arm shows faintly through the mesh, each sleeve ending in a scalloped`
  > `lace edge. ... The sleeve is NEVER smooth and NEVER opaque: never a solid fitted black cap, never`
  > `plain silk or satin over the shoulder.`

- 关键三点：
  1. **`MESH` / `OPEN-WORK` / `eyelet` 这三个词是主力** —— 「scalloped lace」单独不足以让模型画出网眼，
     它会退化成"一块黑布"；必须写明**能透出皮肤底色**（`skin faintly shows through`）。
  2. 负例要指向**"光滑不透明"**，而不是只指向"长袖"（`NEVER smooth and NEVER opaque`）。
  3. 改动要**覆盖全部 5 个服装块**（`WARDROBE` / `_BACK` / `_SIDE` / `_DETAIL` / back 镜的 `headLock`）
     以及 `IDENT` / `REF_NOTE` / `SHEET_NOTE` / `ONE_REF_NOTE` 里回指同一套行头的那几句 ——
     漏掉任何一处，那一类镜就会漂回去。用**全局子串替换**收口最稳（改完 `grep -c` 旧写法必须为 0）。

### §3.24 清洗表要按「各画幅的实际用语」清点，别照抄另一画幅（916-S19 实测）

- 现象：同一个未清洗的句式，在 A 画幅**从不**出问题，在 B 画幅**偶发**双人。
- 真因：`SUBJECT_SCRUB` 是按 169 的写法建的（`a young female singer` / `a young woman`），
  而 **916 全 41 镜里 32 镜写的是不带 `young` 的 `a woman` / `a woman's`** → 这条清洗对 916 全量落空。
  于是 916-S19 在同一份 prompt 下 V8 出单人、V9 出双人（**不稳定 = 不定指没被消除，靠孤立锁硬压**）。
- **可复用的检查动作**：每次换画幅 / 换故事板版本，先跑一遍「**实际用语的清点**」：
  ```bash
  node -e "…扫 storyboard 里 a woman|the woman|a young woman|a young female singer 的分布…"
  ```
  按**清点结果**建规则，不要按"我以为它写的是"建规则。
- **扩表时顺序敏感**：长模式必须排在短模式之前（`of a woman's` → `of HER` 要早于 `of a woman` → `of HER`，
  再早于 `a woman` → `SHE`）。顺序反了会产出 `of HER's face` 这种病句。
- **落表前先干跑**：把表 eval 出来对真实 storyboard 逐镜试算，打印替换结果肉眼过一遍，再烧额度。

### §3.25 「脸部特写」分支必须自带单人锁（169-S11 实测，V9 全量暴露）

- 现象：同一镜 V8 出单人、V9 出**双人（面对面）**，且两版 prompt 的清洗结果只差一个 `'s`。
- 真因：流水线对**脸部特写**有独立分支 ——
  `isFaceCU = /close-?up[^.]{0,60}?\bface\b/i.test(keyframe_prompt)` 命中后**只喂 `ref_face.png` 一张图**，
  并换成 `FACE_REF_NOTE`。这条分支**没有**「EXACTLY one woman」的 HEAD_LOCK 级别约束 →
  只喂一张脸图时，模型把「一张脸」理解成「可以有第二张脸来对望」，自由发挥出双人。
- **修法**：`FACE_REF_NOTE` 及其相邻锁里必须显式写
  `EXACTLY one woman alone in frame, a single face only; NEVER two faces, NEVER a second person, NEVER a profile or mirror-face of the same woman`。
  并把 `ISOLATION` 块同样挂到该分支（原来只有人物镜分支挂了）。
- **✅ 实测有效组合（2026-10-02 修复轮，一次即过）**：
  ① **换参考图**：`CMV_FACE2=1` 改喂 **[ref_face.png, ref_body_front.png] 两张**，并在 refNote 里写死
  「Picture 1 与 Picture 2 是同一个女人，不要当成两个人、也不要把她复制第二份」；
  ② **改文案为具象点名禁止**：把「her face appears exactly ONCE」升级为
  `no second woman, no companion, no side-profile of her, no over-the-shoulder figure`；
  ③ **补回场景锚** —— 原渲染把「雨中湿脸」画成了豪华室内拱廊＋吊灯，因为特写分支只剩一张脸、
  场景句被丢干净了；加一句 `an empty rain-soaked night street out of doors — NOT an interior, NO chandelier, NO palace, NO hallway` 后构图才回到文字。
- **教训**：特写分支缺的不只是「单人锁」，还有**「场景锚」** —— 只喂一张脸图时，模型会用参考图的
  影棚气质自行编造一个华丽内景。修完 S11 从「室内＋双人」变为「雨夜街头＋单人」。
- **可复用的检查动作**：审 `regen-v7.js` 的**每一条 `continue` 分支**，逐条列出它挂了哪些锁
  （HEAD_LOCK / ISOLATION / IDENT / WARDROBE）。**任何一条分支缺「单人锁」都是一个待爆的雷**——
  它平时可能靠别处的锁巧合压住，换个配置就翻车（本镜 V8→V9 就是如此）。

### §3.26 「下摆开花」是全身/远景镜的高频幻觉，且缩略图看不见

- 现象：169-S04、916-S15、916-S27 的裙摆上凭空长出金色牡丹刺绣；
  三镜的 `keyframe_prompt` **全都没有提到花**（S15 全文只有
  `wide shot of a woman in a black cheongsam walking towards …`）。
- 真因：canon 参考图胸口有成对金花，**全身/远景镜**在 i2i 里最容易把「胸口的花」复制扩散到裙摆；
  镜头越远、人物越小，模型越倾向用「加花」来填充大面积黑色。
- **判定铁律**：canon（`ref_body_front.png`）= 胸口**一对**金花 + **裙摆纯黑**。
  任何裙摆/下摆/开衩边的花都是违规，一律 FAIL。
- **可复用的检查动作**：**下摆巡检必须单独做**，且不能靠缩略图——
  用 `CMV_ZONE=lower zoom-sheet.js` 裁下半身放大。
  ⚠️ 注意 `lower` 区对 16:9 只到胸口高度，**169 的裙摆需另裁更靠下的区域**；
  坐姿/半身镜的下摆常被遮挡或出画，属「无法判定」而非「通过」，要单独标出。
- 同类幻觉的通用对策：见下条 —— **但第一版对策是错的，已翻车**。
- **⚠️ 反例（2026-10-02 实测翻车）**：第一版对策写的是
  `… plain solid black silk — NO embroidery, NO flowers, NO peony, NO gold thread and NO pattern of any kind below her neckline`，
  **结果 S04 / S27 的开花比不写锁还重**。原因：把 `flower / peony / gold thread` 这些词喂给模型＝**反向点单**，
  与 §3.16「不要枚举否定」（169-S16 写 `no vendor, no cook, no customer` → 两个候选都画出摊贩）**是同一个坑**。
- **✅ 已验写法（916-S15 一次通过）**：只**正面描述裙摆是什么**，一个花名都不提：
  `From her waist down to the hem the dress is one single unbroken sheet of the deepest matte black silk — seamless, flat, uniform and completely plain, exactly the same solid black fabric as her sleeves.`
  这条对**远景全身镜**有效。
- **难度分层**：远景全身镜（916-S15）一次即过；**中景 / 坐姿镜**（169-S04 坐台阶、916-S27 中景）
  的裙摆在画面里占比很大，模型会持续往大面积黑色上填花 —— 这类镜要**多抽候选选优**
  （同一 prompt 换后缀多跑 2–3 次），别指望一条文字锁解决。

### §3.27 「分叉的服装块」会隐性漂移：局部镜服装块必须与主块同源同步（V9 全量暴露）

- 现象：12 个局部 / 细节镜（169-S05/S08/S17/S19/S32 + 916-S02/S07/S13/S20/S26/S28/S39）的
  领口被画成**宽红滚边**、盘扣被画成**红色**，与 canon 的「细红滚边 + 黑盘扣」明显不同，
  用户报「**是另一种衣服**」。注意这 12 镜在批次验收单上**全被判成 PASS**——
  因为验收备注里把「红滚边」当成了正确特征。
- 真因（两条叠加）：
  1. **漏锚点**。主 `WARDROBE` 块写了 `fastened below by TWO small black knot buttons`，
     而局部镜专用的 `WARDROBE_DETAIL` 块**把「盘扣是黑的」整句漏掉了**
     （只抄了滚边、袖型、裙身底色）→ 模型没有黑扣约束，在「全屏都是衣服」的特写里自行发挥成红扣。
  2. **过度强调**。`WARDROBE_DETAIL` 里为防「滚边变白」写的那句
     `EVERY piping edge on the outfit is deep crimson RED — never white, never ivory…`
     在特写镜里权重被极度放大 → 红边被画成宽条（同 §3.16，强调词在局部镜里会反噬）。
- **判定铁律**（canon `ref_chest_b1.png`）：**滚边＝一根细线的深红；盘扣＝黑丝**。
  任何「宽红边 / 红盘扣」一律 FAIL。
- **✅ 已验写法**（纯文字，试点 2/2 通过）：
  `Its high mandarin collar is jet-black and closes high at the throat, fastened by small round BLACK silk frog buttons sitting on the black collar band … Along the edge of that black collar runs ONE single hairline of deep crimson-red piping: a fine narrow cord, no wider than a thin string …`
- **⚠️ 对照试验反例（重要）**：同一批镜再喂 `canon/ref_chest_b1.png` 当参考图（B 组）**反而更差**——
  构图被劫持成「正面人像＋深V露胸＋胸口双花」，即「喂参考图 → 照抄构图」的老坑。
  → **局部 / 细节镜一律走纯文字路径，不喂参考图**（脸特写除外，它只喂 `ref_face.png`）。
- **通用规则（可移植到任何分层 prompt 架构）**：
  - 只要外观描述被**拆成多份**（人物镜块 / 局部镜块 / 各视角块），
    任何一条外观属性都必须**在每一份里同步存在**；漏掉的那条就是漂移点。
  - **改主服装块之后，必须对局部镜单独巡检一次**：局部镜画面里衣服占比最大，
    细微差异会被放大成「另一种衣服」，而缩略图完全看不出来。
  - 落地动作：按 `grep -E "局部/纯文字|细节镜" run_<suf>.log` 拉出**全部**走该路径的镜，
    一个不漏地重跑（本次是 12 镜；用户肉眼只发现了其中 10 镜，下摆/鞋特写那 2 镜拍不到领口才侥幸躲过）。

### §3.28 「一刀切禁令」会把 canon 的正品一起禁掉（必须改成定点描述）

- 现象：滚边/盘扣修好之后，用户拿 canon 胸口图质问「上面那 10 镜，衣服**为什么不是这个**」。
  这些镜的滚边确实已经对了，但画面里**完全没有那对牡丹**——而 canon 里牡丹就在同一个区域。
- 真因：`WARDROBE_DETAIL` 末句是一句**一刀切禁令**：
  `Every surface of the garment is solid matte jet-black — NO flower, NO peony, NO embroidery and NO gold thread anywhere on it.`
  它本是为防「下摆/袖子乱开花」（§3.26）加的，结果**把 canon 里本该存在的那对牡丹一并禁掉了**。
- **判定铁律（canon）**：花的位置**固定且唯一** —— 水滴口两侧上方 / 锁骨下方，成对、镜像对称。
- **✅ 正确写法 = 定点描述**（不是全禁、也不是全允许）：
  `High on the chest, flanking that teardrop opening at collarbone level, sit her signature MATCHED PAIR of champagne-gold peony clusters — ONE on the LEFT rim and ONE on the RIGHT rim … Everything else on the garment — the collar band, the sleeves, the chest below the opening, the waist and the whole skirt — is solid matte jet-black silk, plain and unpatterned.`
- **通用规则**：每当想写「no X anywhere」这种一刀切否定，**先问一句：X 在 canon 里是否存在？**
  - 存在（本 case 的牡丹）→ 必须改成「X 只允许出现在〈唯一位置〉，其余位置没有」的**定点**写法。
  - 不存在（裙摆的花）→ 仍要避免枚举花名（§3.16），改用正面描述「裙摆是一整片纯黑」。
  - 一句话：**一刀切禁令 = 把正品和赝品一起杀掉。**
- 试点验证（3/3 通过）：916-S28（脖肩）、169-S17（手在胸前）、916-S26 —— 花均**准确落在水滴口两侧**，
  没跑到手上、袖子或下摆；滚边与黑盘扣保持正确。
- ⚠️ 副作用提醒：局部镜走**纯文字路径**，每次重跑**构图都会重新生成**，不能只看衣服，必须逐张目检构图。
- **⚠️ 纠错（2026-10-02 晚）**：本节曾记「916-S26 的『手握湿布包』被画成领口特写」——
  **这条是错的，源于验收拼图标签贴错**。核对 `storyboard.json`：
  **916-S26 的文案本就是 `close-up of a woman's neck and shoulders, collar of a black cheongsam slightly open, skin flushed red`**，
  画面是颈肩特写，**不带手、也不带布包**；「双手紧握湿布包」是 **916-S07** 的文案。
  → 教训：**拼图标签必须从 `storyboard` 抄，不能凭记忆手打**；一张贴错的标签会让后续所有判断（包括用户的）跑偏一整轮。

### §3.29 服装几何必须「单一真相源」；斜襟 + 一列盘扣是模型对 qipao 的先验（第三次「衣服不一致」）

- 现象（用户按 `gate_916_A.jpg` 的 **S12** 点名）：10 个局部镜胸前多出一条**斜襟**（对角红滚边）
  外加**一列盘扣**；开口被画成**窄缝**而不是宽水滴口；牡丹**不对称 / 位置过高**。
  而 canon 与 916-S12 是**正中对称的钥匙孔式开口**：高领 → 一颗黑结扣 → 宽水滴口，
  **没有斜襟，也没有那一列扣**。
- 真因（比 §3.27 更结构性，是「分叉」的第二次复发）：
  1. **主块有几何、局部块没有**。`WARDROBE` 写了
     `Below the collar a WIDE open water-drop (teardrop) keyhole cutout … its widest point measuring about TWO-THIRDS of her chest width`；
     而 `WARDROBE_DETAIL` **从来没抄到这段**（只有 collar + 袖 + 全黑）→ 局部镜的开口几何全靠模型自由发挥。
  2. **复数名词 → 复数渲染**。两块都写 `frog buttons`（复数）→ 模型在胸前**排出一列**盘扣；
     而一列扣必然拖着一条斜襟。canon 是**一颗**黑结扣。
  3. 模型对 `qipao / cheongsam` 的**先验就是斜襟盘扣**——文字留白，它就照先验画。
- **✅ 修法（结构性，一次到位）＝把服装描述收敛成单一真相源**：
  抽出片段 `G_COLLAR / G_TEARDROP / G_FLOWERS / G_SLEEVE / G_BLACK`，主块与局部块**全部由片段拼装**；
  局部镜用「近景派生版」（`G_COLLAR_NEAR / G_TEARDROP_NEAR`，只显式改写「近景会把滚边放大成宽带」这一条，
  其余逐字同源）。另加两句：
  - `G_FRONT_SYM`：`The front of the dress is mirror-SYMMETRICAL about the centre line of her body …`
  - `G_NO_DIAGONAL`：`it carries no diagonal line across the chest and no row of fastenings running down it.`
  **判决：改主服装块之后，任何「另抄一份」的做法都会复发 —— 以后只改 `G_*`。**
- **回归验证（必做）**：重构后要把主块最终字符串与改前**逐字比对**（`eval` 后 `===`），
  防止为了重构把已验收通过的人物镜文案改坏（本次 2527 chars 逐字相同才放行）。
- 试点 **4/4 通过**（916-S28 / 169-S32 / 916-S26 / 916-S26-bundle）：斜襟与盘扣列消失，开口回到正中对称钥匙孔。
- **同日补记 —— 开口「宽度」是第二个漂移点**。斜襟/盘扣列修好后，仍有部分镜把水滴口画成
  **窄高的小孔**（canon / 916-S12 是宽深水滴口，可见上胸与乳沟）。真因：原句虽然写了
  `its widest point measuring about TWO-THIRDS of her chest width`，但被整段长文案淹没、权重不足。
  修法：在**同一片段末尾**补一句强调句 ——
  `This opening is UNMISTAKABLY WIDE and DEEP — a big rounded teardrop: a generous expanse of her bare upper chest and her deep cleavage are visible inside that broad opening.`
  试点 S39 / S13 立竿见影（窄孔 → 宽深水滴口）。
  → 通则：**关键几何量不能只出现一次**；在片段末尾再「点名」一遍，是成本最低、最稳的加固法。
- **两条已知仍会变的东西（重跑前要有心理预期）**：
  1. 局部镜走纯文字路径，**构图每次重掷**（本次 S26 由「领口特写」变成「颈肩」，S13 的手/布包位置也变）。
  2. 领口扣子的形态仍会漂（S39 曾出过一次**金色金属花扣**，canon 是黑丝结扣）→
     已在片段里补材质排他句 `The two buttons are the same matte black silk as the dress itself — never gold, never metal, never jewelled.`
- **可移植规则**：
  - 同一实体（衣服 / 道具 / 人物）出现在多份 prompt 块里 → **必须单源**，禁止各块独立演化。
  - 复数写法会被照复数渲染；只想要一件时写 `ONE …`，并补一句排他句（`… is the ONLY fastening on the front`）。
  - 模型的**先验特征**（此处斜襟盘扣）必须用一句明确的几何否决压掉；文字留白 = 按先验画。

### §3.30 「眼部极特写」为什么永远出胸像 / 脸像：三根绳子 + 一条几何天花板（916-S12，试了 7 版）

**症状**：剧本写 `extreme close-up of a woman's eye, bottom lid tense …`，连续出胸像 / 整脸像，怎么加强构图锁都没用。

**三根把画面往下拽的绳子**（都是纯文字，却能压过构图锁 —— 重申 §3.16「具体名词 > 抽象否定」）：

1. **剧本自带的背景/光色**：本例是 `cold blue lighting, dark background`，深蓝底就是从这里来的。
   要换背景**只改这一处**，别去加"不要蓝色"的句子（那是反向召唤）。
2. `IDENT` 里的身体句：`a very full heavy voluptuous D-cup bust with deep natural cleavage`
   → 派生出 `IDENT_EYE`（断言式删掉胸句，派生未命中就 `process.exit(1)`）。
3. **服装块 + HEAD_LOCK + front 视角锁**：三处都写着「胸口水滴口 / 对称牡丹 / 看得见正面衣服」。
   HEAD_LOCK 原句自带一整句牡丹描述，front 视角锁自带「看得见胸口水滴口」——
   眼特写必须一并换成 `EYE_HEAD_LOCK` / `EYE_VIEW_LOCK`，服装降到「只有画框下缘一条领口黑边」。

**一条几何天花板（最关键的认知）**：**9:16 竖幅在物理上装不下「只有一双眼睛」。**
两眼的横向跨度 ≈ 0.30 脸宽，而 9:16 要求 高 = 宽 / 0.5625 ≈ 0.53 脸宽 —— 正好是眉到下巴。
想只留眼睛，必须把宽度压到 ≈ 一个眼宽（0.07 脸宽），那就是**单眼微距**。
所以：
- 要「一双眼睛 + 眨眼/垂眸表演」→ 竖幅必然带额头与面颊，**接受它是"眼睛插入镜"而非"单眼微距"**；
- 要「真正的单眼微距」→ 锁死单眼，别指望竖幅里塞进两只；
- 文案里写 `her mouth, lips, chin and everything below are OUTSIDE the picture` 这类
  **长串出画声明会翻车**（实测把胸口和披风一起召唤回来）。要么别提，要么用**裁切**实现。

**最稳的落法：先按"单眼微距"生成（构图锁 + 眼区参考图），再对成图做定点裁切成 9:16**。
裁切是确定性的、不掷骰子、不烧额度 —— 比第六、七次改文案可靠得多
（本例 `V16a` 生成后裁到 `y∈[3%,70%]`、以眼睛为横向中心，直接得到"眼+泪+鼻，嘴唇出画"的干净版）。

**可移植规则**：
- 特写镜的"画面里不该出现的东西"，**优先用裁切实现，而不是写进 prompt**。
- 换背景/光色时，**只改剧本里那一句原文**（本例用 `CMV_BG` 做候选对照），不要新增否定句。
- 任何"派生块"（`IDENT_EYE` / `WARDROBE_NECK_ONLY`）都要**断言式派生 + 派生失败即退出**，
  防止上游改了原句、下游静默沿用旧文本（§3.25 单一真相源纪律）。

## 4. 视频端一致性（关键帧对 ≠ 成片对）

> 约定：本节各**条目的序号**即 §4.N（§5 快速索引沿用此名，如第 9 条 = §4.9）。
> 涉及工具：`assets/lint-prompts.js`（§4.9 静态闸门）、`assets/shot-times.js` + `montage.js`（§4.7 反向抽帧）。

1. **video_prompt 注入表演锁**：人物镜加 `NATURAL PERFORMANCE LOCK`（subtle micro-expressions /
   natural breathing / smooth fluid gestures）——v4 轮实测可显著缓解 i2v 面部僵硬。
2. **改了关键帧必须清旧 clips**（坑位 56/60 + 秦淮复现）：videos.js 见已存在 clip 就静默跳过
   （`to generate: 0`），只打一行 ⚠"首帧比成片更新"。正确流程：按该警告清单**归档**旧片段
   （`_archive/old_clips_<原因>_<日期>/`，可回滚），再重跑；关键帧未动的镜头保留复用省额度。
3. **批次运行中改首帧 = 记补跑清单**：视频输入是启动时的 URL 快照，改图不影响已提交任务（坑位 17）。
4. **交付前三道核验**：
   - `ffprobe` 成片 duration/size（SIGTERM 残件核验，空 format = 重跑字幕）；
   - `verify.js` 门禁全 PASS；
   - **从成片反向抽帧**（每镜槽位中心时间）拼核验图交用户终审——这是"成片里还是旧形象"
     （坑位 25）的唯一可靠检测手段。
5. **视频任务的 key 必须钉住创建者**（2026-10-03 实测的 404 风暴）：`POST /v1/videos` 建出的
   任务**绑定在创建它的账号上**。本机 15 个 key 分属多个账号——轮询若轮换 key，只有创建者那个
   能查到任务，其余 14 个一律 `HTTP 404「任务不存在」`。症状：日志被 404 刷屏、整池 key 被误判
   冷却、接着建任务时无 key 可用（叠加服务端 `503 video_queue_full`），看起来像"服务挂了"，
   实际任务在正常推进。修法（已落 `lib/agnes.js` + `videos.js`）：`createVideoTask` 记住
   `usedKey` 并挂到返回对象 `_key`，`pollVideoTask` 收 `opts.key` 后**固定单 key 轮询**，
   且钉住的 key 不参与 `penalize`（404 是"查错账号"，不是"key 坏了"）。
   一句话：**任务级资源必须用创建它的凭据去查**。诊断手法：拿一个正在跑的 task_id，
   用全部 key 各查一次——命中数恰为 1 即确诊。
6. **本地合成/裁切出来的关键帧没有公网 URL，必须"克隆换 URL"，且铁律是本地图 == 远端图**
   （2026-10-03 916-S12 实测）：
   - `.url` 边车**只能由 API 响应写入**（`generateImage` 里 `item.url`），管线**没有独立上传接口**
     → 想让一张本地裁切图能当 `first_frame`，唯一办法是把它当 i2i 输入再走一次生成，拿回托管 URL。
   - 克隆提示词**只描述画面里实际存在的东西**（本例：一只眼睛、眉、泪、暖光、深底、同样的裁切）。
     ⚠️ **千万别把"这张图里没有的东西"写进去**（旗袍 / 披风 / 场景）——那等于反向点单，
     模型会把它们画出来（§3.16 的老坑，在克隆场景同样成立）。
   - 一次克隆 = 一次重绘，**必然有偏差**（本例裁切略放宽，平均绝对像素差 52.91/255）。
     所以：**部署的必须是克隆产物本身**，不能"本地放裁切版、URL 指向克隆版"——
     否则部署图与远端图不一致，成片用的其实是远端那张，§4.4 的反向抽帧会和你以为的对不上。
   - 核验口径：本地部署图 md5 == 下载远端 URL 的 md5（`curl` 下来直接 md5sum 比）。
   - 克隆提示词里补一句 `Do NOT widen the crop, do NOT pull the camera back` 能明显压住画幅漂移。
7. **交付闭环：归档旧成片 → 合成 → 门禁 → 字幕 → 反向抽帧**（2026-10-03 两版双画幅实测，
   操作细节见 SKILL.md「阶段 4/5/6」）：
   - **重跑前先归档上一轮成片**（`05_output/_archive_pre_<轮次>_<日期>/`）。旧成片是"上一版到底
     长什么样"的唯一物证，直接覆盖就再也对不回去了。
   - 顺序固定：`assemble.js --project <dir>` → 六项门禁全 PASS → `subtitles.js --project <dir>`
     → 从**最终字幕版**反向抽帧。
   - **抽帧时刻必须由故事板算，不能用感觉取"60% 处"**：`assemble.js` 按 `shot.duration` 用最大
     余数法分配槽位帧数，所以 `start + (end-start)×ratio` 恰落在该镜自己的槽位内；
     凭感觉取的比例会跨到隔壁镜。工具：`assets/shot-times.js`（`--ids` 点名 / 不点名=全部）。
   - **抽帧对象是最终字幕版，不是 clips**。clips 是输入，字幕版是重编码后的交付物；
     要验就验交付物（§4 标题"关键帧对 ≠ 成片对"的收口）。拼图用 `assets/montage.js`。
   - **核验图必须人眼看**，写实小人物镜尤其（机器布尔判分在这类镜头上会幻觉）。
8. **双画幅并行（16:9 + 9:16）的正确结构**：两版是**各自独立的项目目录**——各有自己的
   `01_plan/storyboard.json`、`02_images/`、`03_clips/`、`05_output/`；共同复用的只有
   `00_source/` 里的歌曲与歌词。因此：改一版的关键帧**不会**影响另一版；
   合成 / 字幕 / 反向抽帧都要**两版各跑一遍**；核验图**分开拼**（横竖画幅格子宽高比打架，
   混在一张里看不清）。**别试图用一份 storyboard 驱动两种画幅**——`aspect` 与构图锁差异太大。
9. **i2v 中途「多长出一只手 / 凭空多出物件」——是 video_prompt 的否定枚举在反向召唤**
   （2026-10-03 916-S02 实测：前 4 秒两只手正常，之后变成 3 只手 + 第 4 条前臂）：
   - **症状**：关键帧是干净的（双手交叠），门禁也全过（motion 达标）；但成片**从某一时刻起**
     肢体数量变了。静态看关键帧永远查不出来 —— 必须在**全时段**抽帧数手（见下面的验证法）。
   - **根因（三条，全在 `video_prompt` 文本里）**：
     1. **否定枚举**。原文连着写了 `no face, no eyes, no head, no torso` /
        `No extra limb, no duplicated hand` / `no second person` —— 按 §3.16/§3.28，
        **枚举否定 = 反向召唤**，"别多画一只手"实际是在点名那只手。
     2. **与首帧自相矛盾**。`BODY-PART LOCK` 声称"全程不得出现躯干"，可**关键帧本身就是
        胸 + 手的构图** —— 提示词和自己的输入打架，i2v 只能"各执行一半"，于是画面开始漂。
     3. **给没有脸的镜头写面部锁**。`NATURAL PERFORMANCE LOCK` 里写着"自然的眨眼、唇部微动"，
        可这一镜根本没有头 —— 又是在召唤头部与躯干回画。
   - **✅ 修法：把否定全部换成「正向的数量锁」**：
     - `COUNT LOCK`：`EXACTLY TWO HANDS — one left hand and one right hand … one woman with
       exactly two arms and exactly two hands. The same two hands are present in every single
       frame from the first frame to the last.`（正向点名数量 + 全程在场，而不是"不要多的"）
     - 动作收敛成**一个明确、单调、不回头**的运动（本例：双手缓缓分开，`a single unhurried
       separation that never reverses`），别让模型自己补戏。
     - 构图锁改成**正向的"与首帧同景别"**（`holds the same close scale and the same amount of
       her body as the first frame`），删掉所有"不要出现 X"。
     - 删掉与画面内容无关的表演锁（无脸镜不写表情/眨眼）。
     - **同步改 `subject_action`**，让 `videos.js` 的 motion-lint 兜底补写时也拿到同一套动作。
   - **开跑前先扫一遍（工具化）**：`node "<skill-dir>/assets/lint-prompts.js" --project <dir>`
     —— 静态扫整份 storyboard，把上面三类句型 + "首帧含手却无数量锁"一次列全（零依赖、不烧额度、
     ERROR 即退出码 1，可当门禁）。**先扫再投**，比出片后回滚便宜得多（HARDENING 坑位 70）。
   - **验证法（不能只看首尾帧）**：连出 **3 条候选**（`videos.js --only S02 --force` 跑 3 次，
     每次把产物另存），对每条做**全宽、高倍、逐 0.5–1s 的手部横带抽帧**再数一遍：
     ```bash
     ffmpeg -ss $t -i candN.mp4 -frames:v 1 -vf "crop=iw:ih*0.16:0:ih*0.54,scale=1400:-1" out.jpg
     ```
     ⚠️ **别用窄裁切**去数肢体——窄裁切会把另一只手切出画外，看着像"只剩一只手"，
     反而更容易误判。要数数量就得**保留整幅宽度**。
   - **挑片权衡**：数量对了之后，优先选**"关键帧的服装/主体全程留在画内"**的那条。
     本例 c2 数量也对，但后段镜头上抬拉远、把旗袍细节甩出画外；c3 全程保留金牡丹 + 水滴口 +
     红滚边 —— 在"服装一致性"是项目主线时，**c3 明显更优**。
   - **同类风险**：i2v 也会**凭空生成关键帧里没有的物件**（本例另一条候选后段长出一盏油灯）。
     挑选时把"新出现的实体"和"数量错误"一起查。
10. **改了关键帧构图，必须同步改 `video_prompt` —— 视频模型服从"文字"胜过服从"首帧"**
    （2026-10-05 9x16 S19 实测，HARDENING 坑位 97）：
    - **症状**：关键帧是**庭院远景**（人约占画面 1/4，用户验收过的 A 版），
      但成片里是**面部特写**（闭眼微笑、泪光）——首尾构图完全对不上。
    - **根因**：一个镜头有两种自相矛盾的描述 —— `keyframe_prompt` 的 `[[SCALE]]` 锚句要求远景，
      而 `shot_size` / `visual` / `video_prompt` 还停在面部特写。图片阶段照 `[[SCALE]]` 画，
      视频阶段照 `video_prompt` 出 —— **首帧被无视了**。
    - **排查**（可复算）：把成片按 assemble 真实槽位抽帧，与对应关键帧做灰度直方图相关；
      `corr < 0.5 且首尾构图肉眼不同` = 高度可疑（S19 = 0.53，全场最低之一）。
    - **修法**：把 `video_prompt` 改写成与关键帧同一构图 + 明确写
      `the camera never approaches her face / there is no close-up`，重跑该镜即恢复。
    - **铁律（核心定律 3「同构律」）**：凡为了构图/尺度改了 `keyframe_prompt`，
      **必须回头检查 `shot_size` / `visual` / `video_prompt` 是否被留在旧景别**，
      改完用 `videos.js --show-prompt` 核对再重跑。
11. **镜内"光漂 / 入夜 / 过曝"——prompt 层拦不住，靠"验证 + 零额度后期兜底"**
    （2026-10-05 9x16 全片实测，HARDENING 坑位 98）：
    - **现象**：首帧是暮色/月光时，视频模型会在 6–10 秒内**自发演出入夜甚至过曝**
      （S19 123→79、S14 固定机位 142→26、S24 131→238）。
      `LIGHT_LOCK_CLAUSE` 之外逐版加强措辞（"it must never darken into deep night"）**两版都照样漂**。
    - **关键判据：先排除运镜**。缓慢拉远会让天空/暗部占比变大、画面自然变暗变蓝 —— 那不是漂移；
      **固定机位（`static`）下出现的任何亮度/色温变化才是真漂移**（S14 铁证）。
    - **处置（零额度、可复算）**：① `assets/drift-check.py`（首帧 vs 尾帧 LAB 亮度差，先排除运镜）；
      ② 对判为真漂移的镜 `assets/stabilize-color.py`（整段拉回本镜首帧水平，
      均值序列先滑动平均防闪烁），再进 assemble。
    - **⚠ 过曝不可逆**：高光细节已丢失的帧只能把亮度拉回、找不回信息 —— **优先别让它过曝**
      （首帧别给太亮的亮部，或缩短单镜时长），后期稳定化只当兜底。
12. **首帧"物理状态"必须在 `video_prompt` 里显式锚定 —— 否则模型让元素去够人物**
    （2026-10-05 9x16 S14/S20/S23 实测，HARDENING 坑位 99/100）：
    - **症状 A（坑位 99）**：首帧她站在干石板上，成片却**站进水里**（裙摆没入、脚下无岸）。
      根因：`video_prompt` 通篇写"水怎么动"、**一句没写"她站在岸上"**，
      而场景盘 `SC4 close` 右侧本来就是河面 —— 模型顺着水的语义把水面扩到她脚下。
    - **症状 B（坑位 100）**：空镜只给了孤立名词（"a flower petal"），模型就造出一朵
      **无茎无根、悬在水面/石板上、比建筑还大**的花。
    - **修法（核心定律 4「没写死的模型会自己改」）**：
      ① **站位锚 + 水位锚 + 构图锚**三句齐上（"全程站在干燥驳岸上、水位保持原位不上涨、
      `the scene does not re-compose`"）；注意 **`static` ≠ 构图锁定**，要单独写"不重新取景"。
      ② **主体成对出现**：写"它是什么"必写"它长在哪"—— 换承载物（石栏上的水珠 / 石榴叶尖的露珠），
      不是换花。
      ③ 排除句 **`keyframe_prompt` 与 `video_prompt` 双双**写死（只改一处 = 坑位 97）。
    - **顺带**：公共块（`GRADE` / `LIGHT`）里的名词（如"花瓣折射的漫射光"）会被每一镜继承，
      既是"风格锚"也是"污染源"—— 某类物体反复乱入时先回头翻公共块。

## 6. 一句话总纲

**基准靠签字，一致靠结构，修正靠单跳 i2i，判定靠布尔+人眼，部署靠闸门，成片靠反向抽帧。**
每一环都有对应的自动化与人工检查点——跳过任何一环的省额度的做法，都会在下一次以十倍额度还回来。

**为什么是这几条？** 它们都是 `references/HARDENING.md` 开篇八条「核心定律」的直接推论 ——
一致性靠共享资产（定律 1）、图能定字不能（定律 2）、一个镜头只有一种描述（定律 3）、
没写死的模型会自己改（定律 4）、控制权归最像目标输出的那张图（定律 5）、
机器只报事实判定归人（定律 6）、修法落进真源（定律 7）、档位有限需求无限（定律 8）。
**遇到新症状，先在定律层定位，再到坑位层找处置步骤。**
