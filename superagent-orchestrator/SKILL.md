# SuperAgent 编排器

## 概述

一句话：**平台组织工作，执行器负责干活；工作可追踪、可恢复、可审阅。**

把用户诉求走成闭环：需求优化 → 需求与验收提炼 → 任务 DAG → 人工确认门禁 → ≤3 路并行执行 → 汇总审查 → 验收与边界检查 → 失败重置恢复 → 交付与复盘。状态落盘、规则由脚本确定性执行，不依赖对话记忆。

## 何时调用

- 诉求包含 ≥3 个可分离子任务，或跨多个文件 / 领域 / 交付物
- 用户要求「并行处理、多任务、编排、调度、拆解、DAG、多 agent 协作」
- 长任务需要中断续跑、失败重试、过程可审计
- 需要海报/信息图/知识地图等视觉成品，且包含生成、排版、审查多个环节
- 用户只给了粗略目标，需要先澄清需求再执行

不适用：单步小任务直接做；纯开放式创意无验收标准时先补需求环节。

## 架构映射（白板 → 本环境）

| 白板层 | 本技能落地 |
|--------|-----------|
| 员工提出工作目标 | 用户原始诉求 + 已有项目上下文 |
| Router 语义协调 | 主 Agent：识别意图、关联已有 plan、分派 worker |
| 控制面（平台规则） | `plan.json` + `plan.state.json` + 权限/额度/并发规则，脚本校验 |
| 调度器 | `scripts/superagent.mjs` 的 `next` / `update` / `status` |
| Worker（独立上下文） | `Agent` 子代理，一任务一份 brief、互不共享上下文 |
| 原生 Agent CLI | 子代理内部的工具调用与多轮执行循环 |
| 交付结果 | `report.md` + 产物文件 + 验收记录 |
| 右侧三项 | 状态持久化 / 用户可随时插话续跑 / 脚本执行确定性规则 |

## 全流程

### P0 接收与关联

1. 判断是否已有同主题的 `plan.json`：有则读取状态**续跑**，不推倒重来；需求变化时走 P1 增量修订。
2. 读取 `status`：若存在长期 `running` 的任务且对应 worker 已中断，先 `update <plan> <taskId> --status pending` 重排；同时查看人工确认状态，`pending` / `changes_requested` 时不得领取任务，先补齐 P3.5。不要删除状态文件，否则丢失重试/重置历史。
3. 检查执行前提与额度：所需工具/权限/目录是否存在；估算 token/耗时预算，超限则拆批或降范围（并发仍 ≤3）。
4. 用户随时插话：先落盘当前状态再响应，不丢弃已完成任务、不推倒重来。
5. 记录「用户当前问题」与「本 run 目标」，一句话写入 plan 的 `goal`。

### P1 需求优化

把原始输入整理为四元组（不确定的写明假设，不空着）：

| 维度 | 要写清的内容 |
|------|-------------|
| 目标 | 完成后世界有什么不同（结果，不是动作） |
| 交付物 | 文件/报告/代码/数据，含路径与格式 |
| 约束 | 时间、依赖、技术栈、风格、不可改变项 |
| 不做什么 | 范围外清单，防止越界 |

歧义分三级处理：
- **阻断**：不问就无法开始 → 用 `AskUserQuestion` 问，**一次最多 3 个**
- **可假设**：给出合理默认并在 plan 中标注 `assumption`
- **可后置**：不阻塞当前路径，记录到 `openQuestions`

### P2 需求与验收提炼

1. 输出需求清单 `R1..Rn`（每条对应一个可交付行为）。
2. 输出验收清单 `AC1..ACm`，每条必须三要素齐全：
   - **判据**：可观测的结果（数值/字段/状态/文件存在）
   - **方法**：怎么验（命令、读取哪个文件、对比什么）
   - **证据**：验收时附上的产物路径或命令输出
3. 判定性自检：换个陌生人能否只凭这条 AC 判 PASS/FAIL？不能就重写。禁止「效果好」「质量高」「体验流畅」这类不可判定项。
4. 验收项同时写入 `plan.json` 的 `acceptance`，任务用 `acceptance` 字段声明覆盖哪些 AC；所有 AC 必须至少被一个任务覆盖。
5. 验证命令必须限定作用域：表格类判据避免宽前缀（不同章节可能都以 `| P` 开头），用唯一编号前缀或脚本断言字段；数值类 AC 用独立实现复算一遍。
6. 视觉/图像类交付（海报、信息图、知识地图）另加五类判据：成品尺寸与格式、无水印/无模型署名、中文可读无乱码、独立审查最终像素、密钥未落盘。AC 配方、生图提示词契约与本地排版规则见 `references/visual-deliverables.md`。

### P3 任务拆解与 DAG 规划

拆解原则：按**交付物**切，不按角色切；单任务可独立验收、可独立重跑；粒度 5–60 分钟机械时间，过大再拆，过小合并。

每个节点必须写全：

```json
{
  "id": "T3",
  "title": "实现调度脚本",
  "deps": ["T2"],
  "inputs": ["plan.json", "references/task-dag-spec.md"],
  "outputs": ["scripts/superagent.mjs"],
  "acceptance": ["AC2", "AC3"],
  "boundary": {
    "inScope": ["validate/next/update/status 四个子命令"],
    "outOfScope": ["不做 Web UI", "不改动其他技能"],
    "stopWhen": "计划校验通过且四命令冒烟通过"
  },
  "priority": 2,
  "estMinutes": 45
}
```

**可并行判定**（四条全满足才允许同批）：
1. 无直接/间接依赖；
2. 不写同一个文件（共享只读输入可以）；
3. 不争用同一稀缺资源（同一 API 额度、同一端口、同一目录写入）；
4. 输出互不依赖，缺谁都能独立验收。

**边界**要点：明确输入边界（读什么）、输出边界（写什么、写哪里）、停止条件（何时算完）、不做清单。写入目标统一在 run 目录，禁止写回技能安装目录。

**输入-依赖一致性**：任务 `inputs` 中的 run 内产物，必须由自身或传递上游的 `outputs` 提供；`validate` 会拒绝“读取其他任务产物但未声明依赖”的计划。要复用已生成底图，不要把依赖砍掉，而是把节点拆成“提示词 / 版式 / 底图 / 合成”，让底图只依赖提示词与 API 规范。

规划完成后：
1. 落盘 `<run-dir>/plan.json`（模板见 `references/task-dag-spec.md`）。
2. 运行 `node scripts/superagent.mjs validate <run-dir>/plan.json`，必须零错误。
3. 标注关键路径；并行度上限硬约束为 3，靠拆分粒度提升吞吐，不靠加并发。

### P3.5 人工确认（执行前门禁）

需求、DAG、审查与验收方案必须先交人工确认，通过后才允许领取任务执行。确认包一次给全，缺项视为未确认：

1. **需求**：四元组、假设、openQuestions。
2. **验收**：R1..Rn、AC1..ACm（判据/方法/证据），以及 AC → 任务的覆盖表。
3. **任务规划**：DAG 节点、依赖、输入输出、边界、并行批次、关键路径。
4. **审查方案**：谁审、审什么、如何保证审查者不参与实现。
5. **依据来源**：RAG/外部资料/数据快照的出处、时效与可信度。
6. **风险**：不可逆动作、外部依赖、API 额度与密钥来源/脱敏、预算与耗时上限。

```bash
node scripts/superagent.mjs approve <run-dir>/plan.json --note "确认说明"
node scripts/superagent.mjs request-changes <run-dir>/plan.json --note "需要修改的点"
```

规则（脚本强制）：

- 未 approve，或 request-changes 后未重新 approve：`next --claim` 与 `update --status running|done` 一律拒绝（退出 1）。
- approve 记录当前计划的 SHA-256 指纹；确认后计划内容再变，旧确认自动失效，必须重新确认。变更影响已完成任务时，先重开相关上游以触发下游重置。
- request-changes 必须写清修改点；记录后回到 **P1/P2** 修订计划，`validate` 通过后重新确认。
- 有任务运行中时拒绝变更确认，先收敛当前批次。
- 预览（`next` 不带 `--claim`）和 `status` 不受门禁影响，可随时查看待确认内容。

### P4 并行执行

前提：P3.5 已 approve 当前计划版本；未通过门禁时 `next --claim` 退出 1。

循环直到无就绪任务：

```bash
node scripts/superagent.mjs next plan.json --claim   # 领取本批（≤3，已自动跳过阻塞）
# —— 对每个领取任务，用 Agent 并行派发（同一批同一消息内发出）——
node scripts/superagent.mjs update plan.json T3 --status done --note "产物+证据摘要"
```

`next` 退出码处理：`2`（无就绪批次且存在 blocked）→ 结束可执行分支，带 blocked 清单进入 P5/P6 汇总上报；`3`（停滞）→ 检查依赖与状态文件，修正后重新 `validate` 再 `next`。
`--claim` 已把任务置为 running 并 `attempts+1`，不要再对同一任务执行 `update --status running`（会双计）。
`next --json` 的 batch 已带 `inputs / outputs / acceptanceDetails / boundary / worker` 与根级 `goal / deliverables / acceptance`，可直接组装七要素 brief，不必回读计划。

派发规则：
- 研究型任务用 `Explore`，方案型用 `Plan`，实现/分析型用 `general-purpose`；复杂任务可在 worker 内再拆，但**不得突破本层 3 并发**。
- Worker 之间不共享对话上下文，只共享 run 目录里的产物文件；因此每个产出必须落盘、可被下游直接读取。
- Worker 回报不合格（无证据、超边界、输出契约不符）视为任务失败，走 P6/失败恢复，不直接汇总。

**Worker brief 七要素**（缺一项就别派）：

```text
[任务] T3 / 标题
[目标] 一句话结果
[输入] 文件路径与上游产物；关键约束
[输出契约] 必须产出的文件/字段/格式/路径
[验收] 对应 AC 的判据
[边界] 只做什么；不做什么；遇到什么情况立即停止并回报
[回报格式] 状态 / 产物路径 / 证据 / 未决问题 / 耗时，≤15 行
```

### P5 汇总与审查

1. 按交付物汇总成草稿，标明每个结论的证据来源。
2. **审查者与执行者分离**：主 Agent 以非执行者视角交叉审查——找矛盾、找缺口、找未证实的事实、找越界产物；任务量大时另派独立 review worker（不参与实现）。
3. 审查发现的问题逐条转成修复任务（通常复用原任务重跑，或新增任务），回到 P4。
4. 审查结论为 FAIL 但审查本身已交付时：先把审查任务置 done，再重开缺陷上游（done→pending），脚本会自动重置其已完成下游；修上游后重跑审查，不带 FAIL 交付。
5. 视觉产物审最终像素，不审 spec：全图 + 100% 裁切（标题、四边、页脚、最小字号、最密区域、底图四角）；审查者不参与渲染，修复后重跑同一组裁切。

### P6 验收与边界检查

1. **逐条 AC 判定**：PASS / FAIL / PARTIAL，必须附证据；PARTIAL 要写清缺哪一部分。
2. **边界三查**：
   - 越界：是否做了 `outOfScope` 里的事、是否改了不该改的文件
   - 缺口：`inScope`/`outputs` 是否有遗漏
   - 泄漏：是否依赖了计划外、未记录的外部输入
3. **交付前密钥扫描**：run 目录不得出现 `sk-` 开头的密钥或私钥块；API Key 只经环境变量传入，命令、日志、报告与图片元数据均不得回显。
4. **计数一致性**：同一事实在 goal、副标题、AC、报告、成品中多处出现时，改一处必须用同一数据源全量重算，禁止“六部分/七部分”这类同文档自相矛盾。
5. 任一 FAIL/PARTIAL 或边界异常：走「失败处理」，不得带病交付。

### P7 交付与复盘

1. 生成 `<run-dir>/report.md`：结论前置 → 交付物清单（含路径）→ 验收表（AC/结论/证据）→ 边界检查 → 未决问题与风险；视觉交付再附生成参数、素材来源、再生成命令与无水印/无乱码检查结果。
2. 项目目录默认整体位于 `<cwd>/out/superagent-<主题>/`（含 `plan/state/work/assets/out/report`），不能只把最终文件复制到 `out/` 而把项目留在根目录；若用户指定其他位置，以用户为准。交付后移动目录，必须同步修正报告中的绝对路径并重新扫描。
3. 复四个指标：并行利用率（实际并行/3）、重试率（失败次数/总尝试）、返工率（被重置的已完成任务/总任务）、阻塞率。
4. 复盘改进动作：拆分粒度是否合理、并行是否被写冲突拖住、验收是否事后才发现不可判定、brief 是否缺要素。
5. 可复用的改进沉淀到本技能 `references/`；一次性的结论留在 report，不写进技能。

## 失败处理与恢复

| 失败类型 | 判定 | 处理 |
|----------|------|------|
| 瞬时失败 | 超时、限流、工具偶发错误 | 同任务重试，可加退避 |
| 结果不合格 | 验收不过、证据缺失、越界 | 修正 brief 后重试；下游结果作废 |
| 上游变更 | 依赖任务重跑导致输入变化 | 重置全部下游任务（含已完成） |
| 规格错误 | 需求/验收本身有歧义 | 回 P1/P2 修订计划，重新 `validate` + 人工确认后再排任务 |
| 阻断 | 缺权限/缺数据/需用户决策 | 标记 blocked，上报，其余分支继续 |

规则（脚本强制执行）：
1. 任务失败后**重置全部传递下游**，包括状态为 done 的；被重置任务 `resets+1`。
2. 同任务重试上限 5 次；失败次数超过 5 才标记 `blocked`（即首次 + 5 次重试）。被重置超过 5 次同样 blocked，防止无限循环。
3. 升级策略：第 2 次失败换方法；第 3 次拆小任务、降范围或换 worker 类型；第 5 次失败上报用户并给出选项。
4. blocked 只影响其下游分支，不阻塞无关分支；全部可执行分支结束后汇总上报。
5. 禁止：伪造完成、静默跳过失败任务、无限重试、失败后直接换题不记录。
6. 重开 blocked 必须先 `--status pending`（脚本拒绝直接置 done/running），重开时失败与重置计数清零；重开已完成任务会自动重置其已完成下游。
7. 人工确认是执行前置条件：确认记录绑定计划指纹，计划变更即失效，禁止带旧确认继续执行。

## 确定性控制面

```bash
node scripts/superagent.mjs validate plan.json              # 计划校验：字段/依赖/环/并发/输入来源
node scripts/superagent.mjs approve plan.json --note "..."  # 人工确认通过（记录计划指纹）
node scripts/superagent.mjs request-changes plan.json --note "..."  # 要求修改，回到 P1/P2
node scripts/superagent.mjs next plan.json [--claim]        # 取就绪批次（≤3），--claim 原子领取
node scripts/superagent.mjs update plan.json T3 --status done|failed|running|pending --note "..."
node scripts/superagent.mjs status plan.json [--json]       # 进度表、确认状态、重试/重置计数、阻塞项
node scripts/smoke.mjs                                      # 自检：校验/确认门禁/领取/失败重置/blocked 守卫
```

退出码：`0` 正常；`1` 计划非法、用法错误或门禁拒绝；`2` 存在 blocked（`next` 仅在无就绪批次时返回 2）；`3` 停滞（无就绪、无运行、未完成且无 blocked）。
完整字段、状态机、确认门禁与重置算法见 `references/task-dag-spec.md`。

## 产物布局

```text
<当前会话工作目录>/out/superagent-<主题>/
├── plan.json          # DAG、验收、边界（唯一计划真源）
├── plan.state.json    # 状态、失败/重试/重置计数、人工确认（脚本维护）
├── assets/            # 可选：生成底图、外部素材
├── work/              # 可选：大纲、脚本、日志、裁切图、独立审查
├── out/               # 可选：项目内最终交付物
└── report.md          # 交付与验收报告
```

项目目录本身整体落 `<cwd>/out/`；会话 `out/` 可再平铺最终 PNG/报告的副本便于取用，但副本不替代项目目录。工作过程中不修改技能自身文件（P7 沉淀除外）。

## 反模式

- 用对话记忆当状态，会话一断全丢
- 跳过人工确认直接开跑，或确认后改计划不重新确认
- 人工提了修改，只改执行不改计划
- 并行任务写同一个文件，互相覆盖
- 一次派 4 个以上 worker 抢额度
- AC 写成「效果好」「体验佳」
- 下游已完成就跳过重跑，拿旧结果拼新交付
- 失败后不分类，一律重试或一律换方案
- 审查由执行者自己做，只复核自己的结论
- 让图像模型直接生成中文正文，再靠反复重生成碰运气
- 只改文案/版式却重新生成底图，白烧额度并引入新水印
- 只审 spec、脚本或 JSON，不审最终像素与 100% 裁切
- 为“复用底图”砍掉依赖，让任务读取尚未产出的上游文件
- 只把最终 PNG/报告复制到 `out/`，项目目录仍留在工作目录根
- 移动项目目录后不修正报告中的绝对路径，导致再生成命令失效
