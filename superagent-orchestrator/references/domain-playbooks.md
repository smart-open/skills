# 领域编排配方（办公 / 调研 / 工程 / 数据 / 内容 / 视觉）

本文件是 `superagent-orchestrator` 的领域适配层。控制面、人工确认门禁、≤3 并行与失败恢复不在这里重复；这里只回答三件事：**怎么拆、怎么验、审查看什么**。

领域配方可以叠加。一个任务同时包含调研、数据和图表时，任务节点应同时满足对应领域的 AC，而不是只挑一个。

## 0. 速查

| 领域 | 拆分主轴 | 推荐 DAG 形态 | 独立审查对象 | 深度材料 |
|------|----------|---------------|--------------|----------|
| 办公 | 文档 / 章节 / 数据口径 | 提取 → 成文 → 复核；多来源则扇出 → 合并 → 一致性审查 | 文件与字段、跨文档一致性 | `office-scenarios.md` |
| 调研 | 子问题 / 来源类型 / 结论 | 问题树 → 多路采集 ∥ 反方检索 → 交叉验证 → 成文 → 独立审查 | 来源、证据链与结论 | 本文件 |
| 工程 | 接口 / 模块 / 迁移步骤 / 测试 | 复现 → 设计 ∥ 测试计划 → 实现 → 回归 → 独立审查 | 代码、命令输出与变更范围 | 本文件 |
| 数据 | 清洗 / 计算 / 独立复算 / 呈现 | 快照 → 校验 → 清洗 ∥ 规则审计 → 汇总 → 复算 → 报告 | 口径、数字与可复现性 | 本文件 |
| 内容 | 结构 / 事实 / 读者 | 大纲 → 事实清单 ∥ 成文 → 事实审查 → 版式/导出 | 内容、来源与最终文件 | 本文件 |
| 视觉 | 版式 / 素材 / 成品 | 大纲 → 素材 ∥ 版式 → 渲染 → 一致性审查 → 成品审查 | 最终成品，不是 spec | `visual-deliverables.md` |

## 1. 办公

### 典型任务

会议纪要转行动项、周报月报、合同/制度审查、项目启动包、批量表格处理、通知与邮件成文。

### 推荐 DAG

- 单文档：`提取结构化信息 → 按模板成文 → 独立复核`。
- 多来源汇总：`多份来源并行摘要 → 合并 → 跨文档一致性审查`。
- 合同/制度：`条款抽取 → 合规 ∥ 风险分级 → 谈判建议 → 报告 → 复核`。
- 批量表格：`清洗 → 计算 ∥ 审计 → 汇总 → 呈现`。

### 验收配方

- 章节、字段、表格列与模板一致；数量可断言。
- 行动项必须有负责人、截止时间、来源；编号全局唯一。
- 跨文档的日期、角色、预算、范围、指标互相一致。
- 关键数字用第二种实现复算，禁止只断言“文件存在”。
- 对外文档检查称谓、语气、收件人和发送范围。

### 审查重点

- 抽查关键行动项是否能回溯到原文。
- 对照模板数章节与字段，不凭印象。
- 多文档交付必须有一致性审查任务，单独看每份都合格不代表合起来一致。
- 检查是否存在“看起来完成了，但没有负责人/截止时间”的空行动项。

### 常见坑

- 宽前缀 `grep` 串表；改用唯一编号前缀或脚本断言。
- brief 没给固定模板，三路并行产出三种结构。
- 把“复核发现 FAIL”当成复核任务失败；应先完成复核，再重开缺陷上游。

已验证样例与指标见 `office-scenarios.md`。

## 2. 调研

### 典型任务

竞品分析、市场/技术选型、资料综述、事实核验、方案比较、决策备忘录。

### 推荐 DAG

```text
问题树
  ├─ 来源采集 A ─┐
  ├─ 来源采集 B ─┼─> 去重与来源评级 ─> 关键事实交叉验证 ─> 结论与建议 ─> 独立审查
  └─ 反方/反证检索 ┘
```

- 每个子问题独立成节点，避免一个 worker 包揽全部检索。
- “采集”和“来源质量评估”分开：来源数量不等于证据质量。
- 关键结论前必须有交叉验证节点；单一来源只能写成线索，不能写成定论。
- 结论与建议分开：建议要写适用条件、代价和不确定性。

### 验收配方

- 每个关键结论都能定位到来源路径/URL、标题和日期。
- 关键事实至少两个独立来源；同源转载不算两个。
- 明确区分事实、估计、观点和推测。
- 至少记录一条反证、冲突证据或未能解释的缺口。
- 引用可解析：链接可打开，或本地文件路径存在；引文上下文没有被截断歪曲。
- 结论逐条回答原始问题，不做“资料堆砌式综述”。

### 审查重点

- 抽查最关键的三条结论，打开原始来源核对，不只读摘要。
- 检查来源日期与适用范围；过期资料不能支撑当前结论。
- 检查“来源存在，但并不支持该结论”的错配。
- 检查是否把供应商材料、软文或单一案例当成行业事实。

### 常见坑

- 用搜索摘要代替原文。
- 只列来源数量，不做交叉验证。
- 结论很确定，但没有任何限制条件或反方证据。
- 把“没找到反证”写成“已被证明”。

## 3. 工程

### 典型任务

新功能、缺陷修复、重构迁移、接口联调、性能优化、测试补齐、自动化脚本。

### 推荐 DAG

- 功能/修复：`复现或建立基线 → 方案 ∥ 测试计划 → 分模块实现 → 集成 → 回归 → 独立审查`。
- 重构/迁移：`现状盘点 → 兼容性 ∥ 回滚方案 → 分批迁移 → 验证 → 清理`。
- 排障：`收集证据 → 复现 → 假设与最小实验 ∥ 影响面分析 → 修复 → 回归 → 复盘`。

实现节点按接口或模块切；不要把“写完后端、写前端、联调、测试”塞进同一个任务。

### 验收配方

- 修复前先有失败证据或基线输出；修复后有同一命令的通过输出。
- 构建、lint、测试命令明确写进 AC，并附实际输出。
- 新增或修改的行为有对应测试；缺陷修复至少有一个回归用例。
- 变更文件清单符合边界，没有顺手重构或改无关文件。
- 对外行为、配置、数据格式变化有迁移或兼容说明。
- 不可逆操作有回滚路径；密钥不落盘、不进日志。
- 性能类 AC 必须有基线、测量方法和阈值，不能写“更快了”。

### 审查重点

- 从干净状态按文档执行构建、测试和复现步骤。
- 审查完整 diff，而不只看新增文件；重点看删除、默认值、异常路径和权限。
- 检查测试是否真的覆盖失败场景，而不是只断言“返回 200”。
- 检查是否引入未声明依赖、生成文件、调试输出或密钥。
- 对迁移/重构，检查旧数据、旧接口和回滚是否可用。

### 常见坑

- 没复现就改代码，最后不知道修的是不是同一个问题。
- 本地能跑但没跑完整测试；或只跑新增测试。
- 修一个 bug 顺带改架构，扩大回归面。
- 只验证成功路径，不验证空值、超时、并发和失败恢复。
- 没有回滚方案就执行不可逆迁移。

## 4. 数据

### 典型任务

数据清洗、指标口径统一、汇总报表、异常排查、分析结论、图表制作。

### 推荐 DAG

```text
输入快照 ─> schema/行数校验 ─> 清洗 ─┬─> 指标计算 ─> 独立复算 ─┐
                                     └─> 规则审计 ────────────┴─> 图表/报告 ─> 审查
```

- 先固定输入快照，再谈结果；输入变了必须重置下游。
- “计算”和“独立复算”分开，优先用不同实现（如 Python 与 SQL/awk）。
- 图表任务只消费已验收的汇总表，不重新定义口径。

### 验收配方

- 输入行数、列数、主键唯一性、日期范围有断言。
- 缺失值、异常值、重复值和排除规则写清楚。
- 指标公式、过滤条件、时间窗口、单位、时区、币种写死。
- 分组合计与总计能对上；关键数字用第二种实现复算。
- 处理脚本可从原始快照重跑，输出可复现。
- 图表中的每个数字能回溯到汇总表或查询结果。

### 审查重点

- 抽查关键分组，手工或独立脚本复算。
- 检查 join 是否放大行数、过滤是否在不同分支不一致。
- 检查时间窗口、时区、币种和单位。
- 检查图表与表格是否使用同一口径。
- 检查异常值是否被静默删除或替换。

### 常见坑

- join 后行数翻倍，指标整体虚高。
- 不同分支用了不同日期范围，最后强行汇总。
- 只验证文件生成，不验证数字。
- “独立复算”实际复用了同一段代码，无法发现同源错误。
- 缺失值直接填 0，改变业务含义。

## 5. 内容与视觉

### 典型任务

技术文章、PPT、海报、信息图、知识地图、课程路线图、封面与配图。

### 推荐 DAG

内容型：

```text
大纲 ─> 事实清单/来源 ─> 成文 ─> 事实与结构审查 ─> 导出
```

视觉型：

```text
大纲/事实清单 ─┬─> 文案与结构 ──────────────┐
               ├─> 素材/底图（只生成无文字资产）┼─> 合成/渲染 ─> 一致性审查 ─> 成品审查
               └─> 版式与视觉规范 ────────────┘
```

- 内容型先锁定大纲、读者和来源，再成文；导出单独验收。
- 稳定资产（底图、模板、设计规范）与易变产物（文案、字号、间距）分开；改文案不重生成底图。
- 事实型内容先有事实清单和来源，再做视觉包装。
- 审查者不参与生成或渲染。

### 验收配方

- 大纲条目全覆盖；章节顺序、术语和版本一致。
- 事实型内容的关键结论有来源；数字与正文、图表一致。
- 导出文件可打开，目录、页码、链接、字体和嵌入对象有效。
- 视觉规格写死：尺寸、比例、格式、字体、最小字号、留白。
- 中文无乱码、无方框；无可见水印、模型名和生成署名。
- 最终成品经独立审查；图像类审像素，不审 spec。
- API Key 未落盘。

### 审查重点

- 内容型先核对大纲与来源，再打开导出文件检查目录、页码、链接、字体和嵌入对象。
- 视觉型先看整体结构与阅读顺序，再看 100% 裁切的最密、最长、最小字号区域。
- 核对标题、目录、正文、图表和页脚是否同一口径。
- 检查图片是否抢字、裁切、重叠、贴边或出现模型署名。
- 事实型文章抽查关键结论的来源，不只看排版。

### 常见坑

- 内容型只审 Markdown 草稿，不打开最终导出文件。
- 大纲漏项或章节顺序变化后，没有重新计数。
- 让图像模型直接生成中文正文。
- 只改文案却重生成底图，白烧额度并引入新水印。
- 只审 spec、脚本或 JSON，不审最终成品。
- 事实内容没有来源，视觉越精致错误越难发现。

视觉专项规则、生图提示词与本地中文渲染见 `visual-deliverables.md`。

## 6. 跨领域组合

| 组合 | 叠加规则 |
|------|----------|
| 调研 + 数据 | 调研 AC 管来源与结论，数据 AC 管口径与复算；图表只消费已验收汇总表 |
| 调研 + 内容 | 先完成事实清单与交叉验证，再进入成文和视觉包装 |
| 工程 + 数据 | 代码 AC 管构建测试，数据 AC 管快照、口径与复算 |
| 办公 + 调研 | 事实来源与模板字段同时验收，不能只满足格式 |
| 办公 + 视觉 | 文档/PPT 同时检查内容一致性、字体、裁切与导出格式 |

组合场景不要合并 AC 表述；保留各自独立判据，避免一个“整体看起来没问题”掩盖单域缺陷。
