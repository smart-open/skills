# 验收与复盘手册

## 1. 需求优化提问库

只在**阻断歧义**时问用户，一次 ≤3 问，其余写成假设。

| 场景 | 问法 |
|------|------|
| 目标含糊 | 「完成后你最先检查的是哪一样东西？」 |
| 交付物不明的 | 「要文件、要结论、还是要能跑的系统？交付到哪里？」 |
| 范围膨胀 | 「这轮必须包含哪些？哪些可以下一轮？」 |
| 口径冲突 | 「A 和 B 两个要求冲突时，以哪个为准？」 |
| 验收标准 | 「什么情况下你会判定这版合格？」 |
| 依赖与权限 | 「数据/账号/目录已就绪吗？我没有 X 权限时谁提供？」 |

假设写法：「假设项目目录为 `<cwd>/out/superagent-<主题>/`；若需其他目录请指出」。假设进 `assumptions`，执行中一旦被证伪，走规格错误分支。

## 2. 验收标准写法

好例：

- 「`out/report.md` 存在且包含 5 个二级标题；`grep '^## ' | wc -l` 输出 5」
- 「接口对空输入返回 400，响应体含 `code=INVALID`（curl 命令 + 输出）」
- 「封面图尺寸 1080×1920，文件 <2MB（identify 输出）」

坏例与改法：

| 坏例 | 问题 | 改法 |
|------|------|------|
| 报告质量高 | 不可判定 | 章节齐全 + 每个结论有出处 |
| 页面好看 | 主观 | 断点 375/1440 无横向滚动；对比度 ≥4.5 |
| 性能优化了 | 无基线 | P95 从 800ms 降到 ≤300ms（同一脚本两次结果） |
| 覆盖主要场景 | 边界不清 | 列出 6 个场景 ID，逐个 PASS/FAIL |

三条硬规则：可观测、可复现、有证据。做不到就说明需求还没提炼完。

**作用域**：表格类验收命令必须限定章节或唯一编号前缀。反例：合同报告的“制度偏差表”和“谈判表”都以 `| P` 开头，`grep '^| P[1-7]'` 会把谈判行一起算进来；应改用 `| P1 |` 等唯一前缀、awk 限定章节，或直接脚本断言列语义。数值类判据至少用第二种实现复算一次。

**计数一致性**：同一事实在 goal、副标题、AC、报告标题、图中文案出现多次时，改一处必须用同一数据源全量重算。反例：AC 写“报告 7 个部分”，任务边界写“六个必备部分”，两者都“看起来对”；验收包应列出章节清单并断言数量，改稿后重新数一遍。

**视觉类 AC 最少覆盖**：
- 文件存在、格式正确、尺寸与宽高比精确（如 5248×2944，非“约 4K”）
- 内容数量与顺序可断言（20 站 × 5 点 + 20 实战，来自同一 outline）
- 无水印、无模型名、无生成署名（源码扫描 + 底图四角/页脚裁切目视）
- 中文可读：无 U+FFFD、无方框/问号替代符，最小字号在 100% 下仍可读
- 最终像素经独立 reviewer 审查，且附全图 + 关键裁切图
- API Key 未落盘：`grep -rE 'sk-[A-Za-z0-9]{20,}' .` 无匹配

细节见 `references/visual-deliverables.md`。

## 3. 执行前人工确认包

P3.5 交给用户的内容，一次给全，按下面骨架输出；没有的项写「无」或「未提供」，不能省略。

```markdown
## 待确认：<主题>

### 1. 需求
- 目标：...
- 交付物：...
- 约束：...
- 不做什么：...
- 假设：...
- 待定问题：...

### 2. 验收
| AC | 判据 | 验证方法 | 证据 |
|----|------|----------|------|

AC 覆盖：AC1→T1,T2；AC2→T2 …（每条 AC 至少一个任务）

### 3. 任务 DAG
| 批次 | 任务 | 依赖 | 产出 | 边界（做 / 不做 / 停止） |
|------|------|------|------|--------------------------|

并行批次 B1=[…]、B2=[…]；关键路径 T1→T2→T5。

### 4. 审查方案
- 审查者：<独立 review worker / 主 Agent 非执行者视角>
- 审查对象：...
- 通过标准：...

### 5. 依据来源
| 来源 | 类型（RAG / 外部资料 / 数据快照） | 时效 | 可信度与限制 |
|------|----------------------------------|------|--------------|

### 6. 风险与预算
- 不可逆动作：...
- 外部依赖：...
- 预计并行轮次 / 耗时：...

请确认：approve；或 request-changes 并写明修改点。
```

用户响应处理：

- 确认无问题 → `approve plan.json --note "确认内容摘要"`，再进入 P4。
- 提出修改 → `request-changes plan.json --note "修改点"`，回 P1/P2 改 plan，`validate` 后重新出确认包。
- 依据来源缺失 → 明确写「未提供」并列入风险，不得假称有 RAG 证据。
- 用户只回「可以」→ note 记录「用户确认执行」；计划指纹由脚本自动绑定，后续改动即失效。

## 4. 边界检查清单

**输入边界**
- [ ] 只读了 `inputs` 声明的材料；计划外输入已登记
- [ ] 外部数据均标注来源与时间

**输出边界**
- [ ] `outputs` 全部存在，路径与格式符合契约
- [ ] 未修改 `outOfScope` 中的文件/系统
- [ ] 产物只写 run 目录，未写回技能或系统目录
- [ ] 视觉成品审的是最终像素，不只看 spec/脚本/JSON
- [ ] API Key 与私钥未落盘：`sk-`/私钥头扫描无匹配

**行为边界**
- [ ] 未超出 `stopWhen` 继续扩展（避免越做越大）
- [ ] 未承诺未验证的结论
- [ ] 失败/未决项已显式列出，没有静默省略

**依赖边界**
- [ ] 下游使用的上游产物是其最新版本（上游重跑后下游已重置）
- [ ] 每个 run 内输入都能追溯到自身或传递上游的 `outputs`
- [ ] 没有隐式共享状态（同一文件并发写、同一额度并发抢）

## 5. 失败分流决策树

```text
失败
├─ 工具/网络/限流类瞬时错误？
│   └─ 是 → 同任务重试（必要时退避），不重置下游
├─ 输出不合格（验收不过/证据缺失/越界）？
│   ├─ brief 缺要素 → 补 brief 重试
│   ├─ 方法不对 → 第 2 次换方法
│   └─ 任务过大 → 第 3 次拆分或降范围
├─ 上游产物变了？
│   └─ 重置全部下游（含已完成）后重跑
├─ 需求/验收本身矛盾？
│   └─ 停下，回 P1/P2 修订计划，重新 validate + 人工确认（不消耗任务重试次数）
└─ 缺权限/缺数据/需人决策？
    └─ 标记 blocked，上报，其余分支继续
```

重试到第 5 次仍失败：停止该分支，上报「已尝试的方案、失败证据、可选路径」，不要继续烧额度。

**审查 FAIL 的处理**：复核任务已经产出可用结论时，审查本身算完成，可置 done；然后重开缺陷上游（done→pending），脚本会重置其已完成下游（resets+1），修复后重跑复核。不要把“审查发现缺陷”当成审查任务失败，也不要带 FAIL 进入交付。

## 6. 复盘指标

| 指标 | 计算 | 看什么 |
|------|------|--------|
| 并行利用率 | 每轮实际并行数的平均 / 3 | 是否拆分过细或依赖过密 |
| 重试率 | failures / attempts | brief 质量、验收是否可判定 |
| 返工率 | 被重置的 done 任务 / 总任务 | 依赖识别、上游稳定性 |
| 阻塞率 | blocked / 总任务 | 前置条件检查是否缺失 |
| 审查命中率 | 审查发现问题数 / 交付物数 | P5 是否走过场 |

改进动作对应：利用率低 → 调拆分与依赖；重试率高 → 改 brief 与 AC；返工率高 → 加强上游验收；阻塞率高 → P0 前置检查。

## 7. report.md 模板

```markdown
# <主题> 交付报告（<日期>）

## 结论
<一段话：完成了什么、是否通过验收、还有什么风险>

## 交付物
| 交付物 | 路径 | 说明 |
|--------|------|------|

## 验收结果
| AC | 判据 | 结论 | 证据 |
|----|------|------|------|

## 边界检查
- 越界：无 / <说明>
- 缺口：无 / <说明>
- 泄漏：无 / <说明>

## 执行统计
任务数 / 并行轮次 / 重试次数 / 重置任务 / 阻塞任务

## 阻塞与未完成分支
| 任务 | 状态 | 原因 | 已尝试方案 |
|------|------|------|-----------|

## 未决问题与建议
1. ...
```

视觉/生成类交付在「交付物」后追加：模型与版本、请求尺寸/比例、生成耗时、素材来源、再生成命令、无水印/无乱码检查结果。

## 8. 汇报口径

- 结论先行，先答「过没过」，再讲过程。
- 每个「完成」都挂证据路径；没有证据的写成「未验证」。
- 失败与未决项放在显眼位置，不藏在附录。
- 对用户只给关键数字与取舍，不倾倒执行日志。
